## 2. 审计发现

### 已修（本轮）

1. **审核不能下架**：`unpublish` 仍要求 `admin`，与“审核可下架”冲突。已改为 `REVIEW_ROLES`，并加用例。
2. **命名空间不能转给审核**：`transfer_namespace` 的目标角色仍只判断 `publisher/admin`，排除了 `reviewer`。已改用 `PUBLISHER_ROLES`。
3. **`store/roles.py` 死代码**：角色常量已定义但未被使用，各处仍是字面量。已把 auth/submissions/catalog 的角色判断统一到常量，避免再次漂移。
4. **账号测试与 KEY 策略冲突**：测试仍断言 `/v1/me` 不含 KEY；已改为断言 `store_key` 与当前 KEY 一致。

### 仍存在 / 需要接受的风险

| 级别 | 发现 | 影响 | 建议 |
|---|---|---|---|
| P1 | `key_plain` 明文入库 | DB/备份泄露即等于 KEY 泄露 | 接受内网取舍；DB 0600、备份加密、限制目录权限 |
| P1 | 旧账号 `key_plain` 为空 | 第一次登录需重新生成一次 | 一次性操作；无法从哈希恢复旧明文 |
| P2 | E2E 每次创建临时作者账号 | 账号表会积累 disabled 的 `e2e.author.*` | 改用固定测试账号或加清理命令；不影响生产 |
| P2 | `ROLE_LABELS` / `role_allows` 未使用 | 小量死代码 | 删除或后续用它们做统一展示/权限判断 |
| P2 | 审核页仍以文本 diff 为主 | 大文件差异阅读成本高 | 折叠/按文件分组；当前功能可用 |
| P2 | 表单只有分组导航，没有字段级错误定位 | 校验失败仍集中在规则列表 | 把 `path` 映射到 `aria-invalid` 和第一个错误 |
| P2 | 限流是进程内滑动窗口 | 多进程/反代后不共享 | 单机生产可接受；网关再加一层 |
| P2 | 无指标端点/审计归档任务 | 生产可观测性有限 | 先靠 health + journald；量大后加指标/cron |
| P3 | 单进程 SQLite | 不支持多副本同时写 | 需要 HA 时先换存储层 |
| P3 | E2E 不进 CI | 前端交互回归靠手动 | CI 有浏览器后加 Playwright 任务 |

## 3. 角色矩阵（现状）

| 角色 | 提交 | 审核/发布/下架 | 审计/贡献 | 用户管理/角色/转移 |
|---|---|---|---|---|
| `member` | 否 | 否 | 否 | 否 |
| `publisher` | 是 | 否 | 否 | 否 |
| `reviewer` | 是 | 是 | 是 | 否 |
| `admin` | 是 | 是 | 是 | 是 |

- 本地账号默认 `publisher`；
- 自审全 kind 禁止；
- 管理员可以审核；审核不能管理用户；
- `reviewer` 账号已从 admin 降为 reviewer，`kwangwah` 保留 admin。

## 4. KEY 与激活（现状）

- 新账号/重新生成后：`key_plain` 持久化，`/v1/me` 返回 `store_key`，连接页直接显示发布配置；
- 旧账号无明文：第一次点一次「重新生成 KEY」，之后持久化；
- 页面只有一个 KEY 面板、一个重新生成按钮，没有粘贴已有 KEY 入口；
- 发布配置直接带 KEY 明文，配置名称固定 `qilin-store` / `qilin-publish`。

## 5. 贡献数据链路

- 提交时服务端覆盖 `author` 快照：publisher_id、username、real_name、nickname、department、job_title；
- 公开 `describe` 只输出 `display_name`；
- 审核页、`get_review`、贡献页、`list_contributions` 可见完整快照；
- 统计按已发布版本，产品数/版本数/类型/最近发布。

## 7. 建议的下一步

1. **P1**：把表单错误按 `path` 落到字段，尤其插件 `PLUGIN_*` 规则；这是目前最影响作者体验的剩余项。
2. **P2**：审核差异按文件折叠，减少长 diff 阅读成本。
3. **P2**：清理 E2E 临时账号，或改成固定测试账号；加一个本地清理脚本。
4. **P2**：删除未使用的 `ROLE_LABELS`/`role_allows`，或让展示和权限共用同一套常量。
5. **P3**：需要多副本时再评估 PostgreSQL/对象存储；当前单机架构与规模匹配。

## 8. 结论

最近一轮把“KEY 不可见、角色混淆、贡献无法统计、审核页信息不足”四个产品问题收掉了，代码层面也修了两个真实权限边界缺陷。当前是**单机生产可用**的状态；剩余风险主要是 KEY 明文带来的数据保护责任、旧账号一次性迁移，以及前端字段级错误和可观测性，不是主链路阻塞。
