### 2.2 审计新发现的反代与部署边界隐患（4 项）

1. **【RP-01 · 高危】反代信任配置失守导致限流绕过与全局登录锁死（DoS）**
   * **线上配置问题**：`host-03:/srv/apps/qilin/.env` 同时设置了 `QILIN_BIND=0.0.0.0`（暴露 `:8787`）与 `QILIN_TRUST_PROXY=1`。`store/http_api.py:192-200` 未校验 TCP 对端 IP 是否为 `10.37.87.25`。网段内或经 SOCKS5 网关接入的任意节点直连 `10.37.87.22:8787` 并伪造随机 `X-Real-IP`，即可绕过 `/v1/login` 与 `/v1/account` 限流；若发送 4,096 个不同伪造头填满 `_RateLimiter.max_keys`（`http_api.py:53-54`），所有真实新 IP 将被无差别拒绝登录/注册长达 5–60 分钟。
   * **仓库代码 + Caddy 模板缺陷**：`deploy/docker/Caddyfile` 未显式覆写 `X-Real-IP`，而 Caddy 默认只向 `X-Forwarded-For` 右侧追加对端 IP；`store/http_api.py:197` 却取 `X-Forwarded-For.split(",")[0]`（最左侧客户端自填值）。若按仓库官方 `compose.yaml --profile edge` 部署，公网攻击者单靠 `X-Forwarded-For` 头即可直接绕过限流或打满限流表。
2. **【RP-02 · 中危】Nginx 日志明文记录一次性上传能力票据 `ticket`**
   * **现场证据**：`host-06` `/srv/proxy/logs/error.log` 在 `2026/11/24 07:39:09` 与 `07:39:24` 因请求体超过默认 `client_body_buffer_size`（16KB）写入临时文件，打印了两行含完整 `?ticket=...` 的 `[warn]` 日志；`access.log` 亦全程明文记录 `PUT /v1/uploads/<id>?ticket=...`。
   * **根因与修复**：`host-06` `:8084` 的 `location /v1/uploads/` 需设置 `client_body_buffer_size 2m;` 与脱敏日志（或 `access_log off;`）；同时商店后端应支持从 HTTP 头 `X-Upload-Ticket` 读取票据，逐步淘汰 URL 查询串传凭据。
3. **【RP-03 · 中危】内网明文 HTTP / 自签 HTTPS 拓扑与校验器强制公网 HTTPS 冲突**
   * `luxi-lab` 统一入口 `:8080–:8084` 为明文 HTTP，`:8443–:8455` 为 `mkcert` 自签根证书 HTTPS；而 `store/validator/validate.py:398,720` 要求所有 `mcp.url` 与外部资源 `url` 必须以 `https://` 开头，且容器内未注入集群 `mkcert` `rootCA.pem`。这导致内网 MCP 服务（如 `:8083/sse`）无法按远程服务登记，只能退化为 `stdio` 桥接脚本。
4. **【RP-04 · 低危】Nginx `upstream app_qilin` 未配 `keepalive` 且需防范超时竞态**
   * `host-06` `luxi.conf` 设置了 `proxy_http_version 1.1; proxy_set_header Connection "";`，但 `upstream app_qilin` 未声明 `keepalive` 连接池；若补充 `keepalive 16;`，必须显式设置 `keepalive_timeout 20s;`（低于后端 `store/http_api.py:188` 的 `self.connection.settimeout(30)`），避免复用已被 Python 端关闭的空闲连接触发偶发 `502`。

### AUD-02（P0 · 阻断长工作流）：MCP 会话固定 1h 硬过期无续期 + 2025-11-25 协议头前置误杀

* **关联反馈**：[反馈-Antigravity客户端MCP接入与制品拉取问题-2026-11-24](反馈-Antigravity客户端MCP接入与制品拉取问题-2026-11-24.md) §1.1
* **源码定位**：
  * `store/http_api.py:134-161`：`_MCP_SESSION_TTL = 3600` 在 `_new_session` 写入固定绝对时间戳 `now + 3600`，`_session_alive` 只校验不续期；且 `sessions` 仅存进程内存，每次更新容器部署即全量丢失，还会跨 Bearer 身份共用。

### AUD-03（P0 · 阻断上架）：`validate` 与 `finish_submit` / `submit_package` 三套入口校验口径割裂（REQ-01）

* **关联问题**：新增问题 1（`REQ-01`），线上实测提交 `5e43ce5bc8a842de` 复现
* **源码定位**：
  1. **静态清单校验 vs 包内文件校验割裂**：`store/mcp_api.py:380-386` 的 `validate` 工具只收 `manifest`，走 `validate_manifest(..., check_files=False)`（`store/validator/validate.py:131-152`），跳过了 `_frontmatter`（`:322-346`）、`_scan_tree`（`:356-376`）、`skill.platform_files` 双向核对（`:461-479`）、`knowledge` 笔记链接与题头（`:231`）、`plugin` 的 `package.json`（`:625-676`）。
  2. **`FRONTMATTER_CONFLICT` 隐藏子串硬规则未写进规范**：
     * `store/validator/validate.py:340-341`：
       `if description and summary and summary not in description and description not in summary:`
       强制要求 `manifest.summary` 必须是 `SKILL.md` frontmatter `description` 的**逐字连续子串**（或反向包含）！一旦作者概括提炼改了一个字即报 `FRONTMATTER_CONFLICT`；
     * `store/validator/validate.py:342-346`：frontmatter 含 `dependency:` 或 `allowed-tools:` 时要求 `manifest.depends` 至少非空；
     * `store/validator/validate.py:334-337`：frontmatter 含非 semver 的 `version` 字符串时要求该原文必须出现在 `manifest.changes` 中；
     * 上述三条硬规则在 `store/protocol.py:84`（`get_spec("skill")`）中仅浓缩为一句模糊的“`name`、`description`、能解析的 `version` 不得和清单说成另一件事”，AI 客户端按规范打包必然踩雷。
  3. **深审新发现 — 小包直传与大包三段上传的 URL 探活双标**：
     * `store/submissions.py:56`（`submit_package` / 门户提交）：`validate_path(root, releases=releases)` —— **`check_urls=False`**；

### AUD-07（P1 · 物理边界对抗与工具规范断层）：大/多文件上传断层及对 `REQ-04` 的底层物理纠偏

* **关联问题**：新增问题 4（`REQ-04`）
* **事实本位（Fact-Centric）硬反馈 —— 为什么不能在商店 MCP 做 `upload_artifact(put_url, zip_path)`**：
  * **物理拓扑限制**：`qilin-publish` 是运行在远端服务器 `10.37.87.22` 容器内的远程 HTTP MCP 服务（`http://10.37.87.25:8084/mcp`），而 `zip_path` 位于发布者本机（如 `10.37.87.13` macOS）的文件系统。远端服务器进程在物理上**不可能跨越网络读取客户端本机路径**。
  * **安全红线**：若在服务端 MCP 实现接收 `zip_path` 读取磁盘并上传的工具，`zip_path` 解析的是服务器容器内路径，不仅 100% 找不到用户本地文件，还会构成**服务端任意文件读取（LFI）漏洞**。
* **断层真实成因**：
  1. `submit_package` 将全部文件 base64 塞入单次工具调用 JSON 参数，受限于 LLM 输出上下文窗口（通常仅能承载数十 KB 文本），超过十几个文件的技能包在模型侧即无法生成调用参数（远早于服务端 8MiB 限制）。
  2. `begin_submit` 已经实现了免 `Authorization` 头的一次性短期能力票据 `put_url`（`/v1/uploads/<id>?ticket=...`），但 `store/mcp_api.py:124` 与 `store/protocol.py:44` 仍沿用早期无 ticket 时代的旧禁令——写着“**不要自己编上传命令 / 不要自己编 curl，在栖林仓库根执行 `python -m store.cli submit <目录>`**”。当作者不在 `LUCY-QILIN` 仓库目录开发技能时，既无 `store.cli` 可调，又被规范禁止对 `put_url` 发 `PUT`，造成人为操作死锁。
* **符合网络物理定律的修正路径**：
  1. **开放并标准化客户端对 `put_url` 的受控 HTTP PUT**：`begin_submit` / `begin_revise` 返回值除 `put_url` 外，直接下发标准无密钥泄露的上传指令模板（或明确允许客户端本地工具链对 `put_url` 发送二进制 `PUT` 请求，无需携带 `QILIN_STORE_KEY`），同步更新 `protocol.py` 的 `upload` 规范。
  2. 本地 CLI `store submit <dir>` 保持为大包首选批处理入口（支持任意工作目录通过 `pip install -e` / 全局命令调用）。
