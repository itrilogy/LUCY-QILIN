# 知识包范式设计：从笔记库到可审核的知识包

日期：2026-11-16。依据三份调研：`KNOWLEDGE-DECOMPOSER` 技能的既有约定、Obsidian 笔记库 8691 篇的题头与标签统计、`.reasonix/memory/global` 的企业背景（只读 `company-*`、`dept-*`、`MEMORY.md`，跳过了密钥、家庭与个人档案）。

本文回答一个问题：**知识包到底该长什么样，商店该管到什么程度，词表从哪来、怎么改。**

**执行状态（2026-11-16）**：规格第 4.9、4.10、5.1、12 节已按本文件修订；校验器 v2 已实现（17 条负例见 `tests/test_knowledge_v2.py`）；六份数据资源已由 MCP 下发。未做：真实包迁移、门户展示、`qilin://example` 之外的样例。

结论先写：

1. **一包一主题，一篇一件事。** 包是「一组能自己闭合的笔记」，不是整个笔记库的镜像。
2. **分类按业务条线，不按产出形态。** 产出形态交给 `type` 与 `tags`，不要混进 `business_category`。这是笔记库调研里最值得记的一条：现有两套分类哲学（业务域 vs 工作产出）零交叉，混用会得到两套互斥的 12 类。
3. **词表封闭、带版本、可机器读。** 协议由三份文件组成：分类词表、标签词表、元数据词典；`business_category / business_domain / knowledge_kind` 只认词表，新增要升版本；标签是受控命名空间，不是自由文本的垃圾场。
4. **商店只判「能不能闭合」，不判「写得好不好」。** 但闭合现在包括：入口是导航篇、链接与锚点存在、标签合规、密级不越级。孤篇只警告，不阻断。
5. **密级是声明，不是访问控制。** v1 只要求写清楚并在门户显示，不做按人授权；别把「写了 confidential」当成「已经加密」。

## 1. 调研事实（决定设计的三组数据）

### 1.1 技能约定（KNOWLEDGE-DECOMPOSER）

可直接借鉴：

- 文件名 `NN-名称.md`，导航篇固定 `00-导航概览.md`，它是唯一入口；
- 题头必填 `type`、`status`、`created`、`updated`、`tags`；`tags` 是带层级的数组；
- `aliases` 只用于搜索与显示，**不能作为 `[[链接]]` 的目标**；
- 含 `[[链接]]` 的题头字段必须是数组（`prerequisite` 最容易写错）；
- 断链为 0 才允许上架；每篇至少被引用一次（孤篇检查）；
- 知识空白补全：本地查询 → 外部检索 → `> [!note] 待补全` 标注 → 推荐 2–3 个生长点。

不照搬：

- `_知识图谱总览.md` 的全局 Mermaid 图：篇数一多就不可维护，且与 `NN-` 规则冲突。改为「每包一个入口，导航篇里放局部地图」。
- `cssclass`、`target_audience`、三种阅读路径、人格基底：属于 Obsidian 展示层与写作风格，不进商店契约。
- 「涉当代中国政治人物/事件/政策」的内容红线：与商店「不审内容」的边界冲突，留给发布方与审核人。

技能自身还有三处矛盾，不继承：`qilin-upload.md` 明明存在，SKILL.md 却说「不要在 references 里找上架步骤」；`prerequisite` 三处写法不一致；断链正则没有代码块豁免，会把示例里的 `[[...]]` 误报。商店的校验器按本文的规则来，不按这三处。

### 1.2 笔记库（8691 篇）

| 事实 | 数字 | 对设计的含义 |
|---|---|---|
| 有 YAML 题头 | 2750 篇（31.6%） | 题头是少数派，不能假设全库都能直接打包 |
| 有任意标签 | 2219 篇（25.5%） | 74.5% 无标签；**不要试图给全库补标签** |
| 题头标签只出现一次 | 70.2% | 现有标签是长尾，不能直接当词表 |
| 题头标签带 `前缀/` 分面 | 8.4%（185/2170 篇） | 分面标签已有雏形，但未统一 |
| inline 标签 | 仅 71 篇（0.8%），其中 60% 来自 3 个「标签规范」文件 | inline 标签不是可靠数据源 |
| 中英/大小写/单复数变体 | AI/人工智能、LLM/llm、MOC/moc 等 | 词表必须给 aliases，并规定小写 |

两套分类哲学：一套是按业务条线（党建引领、便民服务、专卖监管、客户经营，267 篇），另一套是按产出形态（`type/`、`status/`、`项目/`、`saf-ti/`），两者**零交叉**。这直接决定了本文的三面模型。

### 1.3 企业画像（记忆文件）

政企合一、专卖专营；市公司经营、县级局执法；板块是专卖执法、卷烟营销、物流配送、烟叶与生产协同、综合管理；知识形态集中在体系文件、案件卷宗、投放策略、作业标准、预算口径、审计整改、项目申报与验收。由此得到 10 个企业类目（含党建与社会责任、标准化与精益），加上知识工作侧的科研、内容、人文、决策、学习、语言、AI、知识运营，共 18 类。

## 2. 三面模型：业务、形态、标签

不要把三件事塞进一个字段：

| 面 | 字段 | 回答的问题 | 取值来源 |
|---|---|---|---|
| 业务 | `business_category` / `business_domain` | 这篇讲的是哪条业务线 | 封闭词表（12 类 / 59 域） |
| 形态 | 笔记 `type` + `knowledge_kind` | 它是参考、指南、教程、反思还是导航 | 5 个固定值，与技能一致 |
| 标签 | `tags` | 涉及哪些概念、实体、方法、来源 | 受控命名空间，至少一个 `topic/` |

业务面决定知识树落点（`<category>/<domain>/<kind>/<id>/<version>`）；形态面决定「怎么读」；标签面决定「怎么搜」。三者互不替代。

**取舍**：`knowledge_kind` 只用 5 个值，和笔记 `type` 一一对应（`reference_note` → `reference`，`map_of_content` → `moc`）。不另造一套「concept / spec / case / data / transcript」枚举——它们都是 `reference` 的细分，用 `tags` 表达。理由：两套形态枚举必然漂移，而现有技能与校验器已经统一在 5 个值上。

## 3. 协议与词表 v1：三份文件

这一节是**商店 MCP 下发的生产协议**，不是对笔记库的描述。笔记库只用来证明词表覆盖得够不够。协议由三份可机器读的文件组成：

| 文件 | 内容 | 谁读 |
|---|---|---|
| `store/spec/knowledge-vocabulary.json` | 18 类目 / 91 领域 / 5 形态 / 4 密级 / 2 范围 | 校验器、清单、树路径 |
| `store/spec/knowledge-tags.json` | 4 个标签分面 / 167 个核心词 | 作者、检索、审核 |
| `store/spec/knowledge-metadata.json` | 包、笔记、知识技能的字段字典 + 10 阶段生产流程 | 作者、审核、MCP 资源 |

题头的形状另有 `store/spec/knowledge-note.schema.json`。四份文件都归 `kv/1` 管，改任何一份都要升版本。2026-11-16 起，这四份文件已通过商店 MCP 的 `resources/list` 与 `resources/read` 下发（见 7.1）。

### 3.2 形态（5）、密级（4）、范围（2）

| kind | 中文 | 对应 `type` |
|---|---|---|
| `reference` | 参考 | `reference_note` |
| `guide` | 指南 | `guide_note` |
| `tutorial` | 教程 | `tutorial_note` |
| `reflection` | 反思 | `reflection_note` |
| `moc` | 导航 | `map_of_content` |

密级：`public` / `internal`（默认）/ `restricted` / `confidential`。包级必填，篇级可选且不得高于包级。

范围：`enterprise`（企业知识）/ `work`（个人或团队的知识工作产出）。

### 3.3 标签词表：4 个分面，167 个核心词

| 分面 | 模式 | 词数 | 规则 |
|---|---|---|---|
| `topic/` | 核心 + 本地 | 103 | 每篇至少 1 个；包内可声明最多 10 个 `knowledge.topics` 本地词 |
| `entity/` | 开放 + 核心 | 25 | 组织、产品、系统、标准专名；优先用核心 id |
| `method/` | 封闭 | 26 | QC 七工具、TRIZ、DMAIC、PARA、渐进式总结等 |
| `source/` | 封闭 | 13 | 政策文件、标准、期刊、公众号、纪要、数据集等 |

标签写作 `<facet>/<slug>`；slug 小写英文或中文，段内用 `-`，全程 1–12 个标签。`status/`、`type/` 这类分面不再用标签表达，改用同名字段。

**为什么 topic 是半封闭**：103 个核心词覆盖常见主题，但不可能穷尽。允许每包声明最多 10 个本地词，审核时决定是否提升为全局词。这样既不阻塞作者，也不让全局词表被长尾污染。

### 3.4 元数据词典

`knowledge-metadata.json` 把字段写成可审核的字典，分两组，另加一个可选溯源字段：

- **包级**：`knowledge.entry`、`taxonomy` 三段、`security_level`、`scope`、`vocabulary`、`language`、`license`、`topics`、`knowledge_map`，以及 `meta.tags`。
- **笔记级**：`type`、`status`、`created`、`updated`、`tags`、`title`、`aliases`、`prerequisite`、`summary`、`security_level`、`domain`、`knowledge_kind`、`source`。
- **溯源（可选）**：`knowledge.producer`。只记录技能 id、工具名或「人工」，不参与校验。

每个字段都写了类型、必填性、取值来源、语义与默认值。审核页可以按这份字典逐项核对，而不是靠记忆。

### 3.5 生产过程：10 阶段（与生产者无关）

`knowledge-metadata.json` 的 `workflow` 定义了生产知识包的固定流程。它描述「做什么检查」，不规定「用哪个技能做」；商店只验收产物，不运行流程。

| 阶段 | 产物 | 关键检查 |
|---|---|---|
| `scope` 定题与边界 | 一句话主题、包范围 | 单一主题、10–30 篇、说清不包含什么 |
| `collect` 采集与清洗 | 素材清单 | 来源可标注、去重、剔除密钥与隐私 |
| `decompose` 原子化拆解 | 概念清单 | 一篇一件事、概念可命名 |
| `cluster` 语义聚类 | 主题簇 | 簇内聚、簇间有桥接 |
| `outline` 导航与结构 | `00-导航概览.md` | 入口覆盖所有板块、阅读路径清晰 |
| `write` 逐篇撰写 | `NN-*.md` | 题头完整、摘要一句话 |
| `link` 双链与锚点 | 链接清单 | 无断链、锚点存在、无孤篇（入口除外） |
| `validate` 本地校验 | `store validate` 报告 | 没有 error、词表命中、密级不越级 |
| `package` 清单与打包 | `manifest.json`、zip | taxonomy 齐全、entry 正确、大小上限 |
| `submit` 提交审核 | `submission_id` | `pending`、钥匙不进输出 |

禁用项：写密钥、引用包外笔记、子目录、未校验就提交、手改已发布版本。

**生产技能不属于本协议。** 笔记可以由用户从商店下载的技能生产，也可以由自建技能或人工生产；商店不登记生产者，也不因为某个技能没被登记就拒收。协议只约束产物：分类、标签、密级、入口、链接、命名、大小。需要溯源时，用可选的 `knowledge.producer` 记录技能 id 或「人工」，它不参与校验，也不授予任何权限。商店里的 `kind=skill` 商品有自己的清单，与知识包协议互不依赖。

### 3.6 词表治理

- 词表有 `version`（`kv/1`）。包清单用 `knowledge.vocabulary` 固定版本；不带则按当前版本校验。
- 新增 category/domain 必须：给出定义、至少一个来源、至少 3 个示例笔记；升次版本（`kv/1.1`）。
- 改名不删 id：旧 id 标 `deprecated`，保留至少两个版本；新包用新 id。
- 别名（`aliases`）只用于**读取旧包**，不用于新包；校验器不做模糊匹配。
- 本地词（`knowledge.topics`）在审核时要么提升为全局词，要么在下一版删除；不能长期停留在包里。

## 4. 笔记规范

### 4.1 文件名与入口

- 正文笔记：`NN-名称.md`，`NN` 为 01–99；同一包内不重复。
- 入口：`00-导航概览.md`，必须是 `map_of_content`，必须链接到每个一级板块。
- 不再要求 `_知识图谱总览.md`；如需要全局图，放在入口篇的 Mermaid 块里，且只画一层。
- 包内平铺，无子目录，无图片；`manifest.json` 与笔记并列。
- `SKILL.md`、`README.md` 不作为知识笔记收录（`NOTE_FILE`）。

### 4.2 题头

机器可读契约：[`store/spec/knowledge-note.schema.json`](../store/spec/knowledge-note.schema.json)。

必填：

| 字段 | 约束 |
|---|---|
| `type` | 5 个值之一 |
| `status` | `evergreen` / `seedling` |
| `created` / `updated` | `YYYY-MM-DD`；`updated >= created` |
| `tags` | 数组，1–12，至少一个 `topic/` |

可选：`title`（≤80 字）、`aliases`（≤8，不得作为链接目标）、`prerequisite`（数组或「无」）、`summary`（≤200 字）、`security_level`、`domain`、`knowledge_kind`、`source`。

禁止：题头里写密钥、口令、token、身份证、手机号；出现即 `SECRET_PATTERN`。

解析兼容：UTF-8 BOM、CRLF、`tags: [a, b]` 流式数组、`description: >` 折叠标量都接受（本轮已修，见 `tests/test_knowledge_parser.py`）。`tags: a, b` 这种字符串写法拒绝。

### 4.3 链接

- 只认 `[[篇名]]`、`[[篇名|显示]]`、`[[篇名#标题]]`；`![[篇名#标题]]` 按嵌入处理，同样校验目标。
- 篇名是文件名去掉 `.md`；别名不是合法目标。
- 代码块与行内代码里的 `[[...]]` 不校验（修掉技能正则的误报）。
- 目标篇必须存在（`NOTE_LINK`）；锚点标题必须存在（`NOTE_LINK`）。
- 孤篇（没有任何入链）只警告 `NOTE_ORPHAN`，不阻断；入口篇豁免。
- 自链允许；循环链接允许。

### 4.4 包级字段

```json
"knowledge": {
  "entry": "00-导航概览.md",
  "taxonomy": {
    "business_category": "innovation-project",
    "business_domain": "qc-improvement",
    "knowledge_kind": "guide"
  },
  "security_level": "internal",
  "vocabulary": "kv/1",
  "knowledge_map": { "nodes": [ ... ] }
}
```

- `taxonomy` 从「可选」改为**必填**。没有分类的包无法进入知识树，也无法被检索。
- `security_level` 必填，默认 `internal`；篇级不得高于包级。
- `knowledge_map` 仍可选；节点必须指向包内笔记。
- `knowledge_kind` 是包的默认形态；篇级 `knowledge_kind` 可覆盖，但必须与 `type` 对应。

## 5. 校验规则变更（2026-11-16 已实现）

| 规则 | 现在 | 变更后 | 规则 id |
|---|---|---|---|
| 分类 | `taxonomy` 可选，只查字符 | 必填；三段必须在词表内 | `KNOWLEDGE_TAXONOMY` |
| 入口 | 存在即可 | 必须 `00-*.md` 且 `type=map_of_content` | `NOTE_ENTRY` |
| 题头 | 5 字段 | 加 `updated>=created`、tags 命名空间与数量 | `NOTE_FRONTMATTER` |
| 标签 | 任意数组 | `topic|entity|method|source` 前缀，至少 1 个 `topic/` | `NOTE_FRONTMATTER` |
| 密级 | 无 | 包级必填；篇级不得越级 | `NOTE_SECURITY`（新） |
| 链接 | 目标存在 | 目标 + 锚点都存在；代码块豁免 | `NOTE_LINK` |
| 孤篇 | 不查 | 警告，不阻断 | `NOTE_ORPHAN`（新，warning） |
| 命名 | 不查 | `NN-` 或 `00-`；`SKILL.md`/`README.md` 拒收 | `NOTE_FILE` |
| 大小 | 无 | 单篇 ≤256KiB；整包 ≤8MiB | `NOTE_FILE` |

`NOTE_SECURITY`、`NOTE_ORPHAN` 已进规格第 12 节与 `store/errors.py`；规则契约测试强制两边同步。实现见 `store/validator/knowledge.py`，负例见 `tests/test_knowledge_v2.py`（17 条）。

**不做**：文章质量、孤篇阻断、标签语义相似度、图片与外链抓取、按人 ACL。

### 6.2 题头 → 词表

- `type`：`reference_note/guide_note/tutorial_note/reflection_note/map_of_content` 原样；`concept`、`research_note`、`product_definition`、`material_card` → `reference_note`；`extension`、`engineering-note` → `guide_note`；`case` → `reference_note` + `topic/案例`；`raw_transcript` → `reference_note` + `source/transcript`。
- `status`：`evergreen` 原样；`reviewed`、`complete`、`completed`、`active`、`完成`、`定稿`、`verified`、`cleaned`、`engineering-aligned` → `evergreen`；`draft`、`in-progress` → `seedling`。
- `tags`：裸标签加 `topic/`；已知实体（工具、产品、标准名等）加 `entity/`；方法（QC、TRIZ、精益、六西格玛）加 `method/`；`status/`、`type/` 分面删除，交给字段。
- 中文标签保留中文，但同一概念只留一个写法；`AI`/`ai`/`人工智能` 统一为 `topic/ai`（中文名放 `aliases`）。

### 6.3 不迁移的

- 74.5% 无标签的笔记：不批量补题头。要打包时按包的主题抽出 10–30 篇，逐篇补。
- `personal-profile`、家庭与凭据：永不进入知识包。
- `_grok_knowledge_map` 里的自动生成索引：不复制到包里，只在入口篇里重建。

## 7. Harness 怎么读到、怎么修订

### 7.1 MCP 资源（新增）

| URI | 内容 |
|---|---|
| `qilin://spec/knowledge` | 散文规范（现有） |
| `qilin://schema/knowledge` | 笔记题头 JSON Schema |
| `qilin://vocab/knowledge` | 分类词表（18/91/5/4/2 与别名） |
| `qilin://tags/knowledge` | 标签词表（4 分面 / 167 词） |
| `qilin://metadata/knowledge` | 元数据词典 + 10 阶段生产流程 |
| `qilin://checklist/knowledge` | 由流程生成的自检清单 |
| `qilin://example/knowledge` | 最小合格包（3 篇：入口、指南、参考） |

六项都已接入 `protocol.py` 与 `mcp_api.py`：`resources/list` 同时列散文规范与六份知识资源，`resources/read` 按 MIME 类型返回 JSON、Schema、Markdown 或 `text/plain`。

`get_spec` 的返回增加 `version` 与 `hash`（正文 sha256），规范一改 hash 就变，客户端据此决定要不要重读。

### 7.2 固定工作流

1. `get_spec("knowledge")` → `qilin://schema/knowledge` + `qilin://vocab/knowledge`；
2. 读 `qilin://checklist/knowledge`，按清单整理 10–30 篇；
3. 在本机跑 `python -m store.cli validate <目录>`（这是唯一读到全文的校验）；
4. 通过后 `python -m store.cli submit <目录>`；
5. `pending` 后由审核发布；失败按 `rule` 与 `path` 改，不改规则。

商店仍然不运行知识分解技能，也不判断文章好不好。
