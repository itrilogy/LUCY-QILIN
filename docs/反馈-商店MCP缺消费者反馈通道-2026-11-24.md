# 反馈：商店 MCP 缺一个消费者反馈通道

- 反馈日期：2026-11-24
- 反馈来源：用商店 MCP 装一个上架商品时的实际卡点
- 性质：产品能力缺口（建议）

## 一、现状

商店 MCP 在本次会话里对匿名/普通使用者可见的工具，全部是“查询”或“上架/审核/管理”：

- 查询类：`get_spec`、`search`、`list_versions`、`resolve`、`describe`、`install_plan`、`artifact`
- 上架类（作者 KEY）：`validate`、`begin_submit`、`submit_package`、`finish_submit`、`begin_revise`、`finish_revise`、`list_my_submissions`、`get_submission`、`withdraw`
- 审核/管理类：`list_reviews`、`get_review`、`review_plugin`、`approve`、`reject`、`unpublish`、`list_audit`、`list_contributions`、`transfer_namespace`

也就是说：**使用者能看见、能取安装计划、能下载，但没有任何回传“我装了，出问题了”的入口。** 唯一能触达作者的是 `reject` 的 `reason`，而它只作用于“待审核的提交”，对已发布版本无效；使用者也没有审核角色。

## 二、影响

- **问题只能绕道。** 本次遇到 `kind=mcp` 的制品缺失，使用者没有任何地方可报；只能自己写桥接把功能装上，再把问题留在本地对话里。商店侧对此零感知。
- **作者拿不到真实安装结果。** 静态校验通过 ≠ 装得上。安装失败率、平台相关失败、文档与实物不符，这些只有使用者知道。
- **已发布版本缺少纠错回路。** `unpublish` 是审核/管理员动作，不是“有人报告后才复核”；没有问题池，管理员也无从判断哪些版本该优先复核。
- **匿名使用者完全失声。** 按现有口径，未登录也能浏览、读规范、取安装计划、下载制品；这批人反馈成本最高，也最容易踩坑。

## 三、建议：最小闭环（供评审，不指定实现）

一个够用的闭环只需要“交得上来、作者看得见、审核能分诊、状态能收敛”四件事。

### 3.1 建议的工具面（命名与参数仅供评审）

| 工具 | 谁可用 | 作用 |
|---|---|---|
| `report_problem` | 匿名 + 任意角色 | 对某个 `id@version` 提一条反馈：类别（装不上/制品缺失/文档不符/其他）、现象、复现步骤、环境（客户端、平台）、可选联系方式 |
| `list_my_reports` | 有身份者 | 自己提过的反馈与处理状态（匿名提交不发令牌，靠提交时返回的 `report_id` 查） |
| `get_report` | 提交者 / 作者 / 审核 / 管理员 | 单条的正文、状态、处理结论；正文按角色裁剪 |
| `list_product_reports` | 该产品作者 | 自己命名空间下产品的反馈列表，按版本与类别聚合 |
| `list_reports` | 审核 / 管理员 | 分诊队列，可按 `id`、`kind`、`category`、`status` 过滤 |
| `triage_report` | 审核 / 管理员 | 改状态（`open → triaged → resolved / rejected`），可写对作者与提交者都可见的结论；`resolved` 时必须给出结论 |

不建议把反馈做成“能直接下架”的动作：下架仍走 `unpublish`，反馈只提供判断依据。

### 3.2 权限矩阵（与现有角色一致）

| 动作 | 匿名 | 作者 | 审核 | 管理员 |
|---|---|---|---|---|
| 提交反馈 | 是（限流） | 是 | 是 | 是 |
| 看自己的反馈 | 凭 `report_id` | 是 | 是 | 是 |
| 看自己产品的反馈 | 否 | 是（限自己命名空间） | 是 | 是 |
| 分诊/改状态 | 否 | 否 | 是 | 是 |
| 看全部反馈 | 否 | 否 | 是 | 是 |

### 3.3 硬约束（建议写进规范，避免变成滥用入口）

- **限流**：匿名按来源与 `id` 双维度限流；已登录按账号限流。命中时返回明确规则，不要静默丢弃。
- **体积**：正文与复现步骤都要有字符上限，超限拒收而不是截断保存。
- **去密**：反馈正文不得包含密钥样式内容；命中即拒收（与上架包同一套判据），不要打码后放行。
- **不代理流量**：反馈只存文本与元数据，不允许附带可执行文件或外链下载。
- **审计**：`report.create`、`report.triage` 进审计；审计只记动作与 `id/version`，不记正文全文。
- **可见性**：作者只能看到自己命名空间下产品的反馈；跨作者不可见。审核/管理员可见全文。
- **生命周期**：反馈不随版本下架消失，绑在 `id` 上、标注 `version`，便于区分“某版本的问题”。

### 3.4 与现有流程的边界

- 不替代 `reject`：审核退回仍只针对待审核提交，反馈针对已发布版本。
- 不改清单：反馈不修改 `manifest`、`changes` 或制品；要改内容仍由作者发新版本。
- 不参与安装计划：`install_plan` 的输出保持纯净，不混入反馈统计。
- 可选：`describe` 或门户产品页展示“该版本已知问题 N 条 / 最近一次处理结论”，但默认不阻塞安装。

## 四、可验收的判定

1. 匿名用户可以成功提交一条针对 `id@version` 的反馈，得到 `report_id`，并能凭它查询状态。
2. 该产品作者能在自己的列表里看到这条反馈，看不到其他作者的。
3. 审核员能把状态从 `open` 推到 `triaged`，最后到 `resolved`（必须写结论）或 `rejected`（必须写原因）。
4. 超限、含密钥样式内容、缺 `id`/`version` 的提交都被拒收，并返回可读规则。
5. 审计里能看到 `report.create` 与 `report.triage`，但看不到正文全文。
6. 匿名提交不会创建账号、不会拿到 KEY、不能借反馈接口做写操作。

## 五、为什么现在提

本次是“使用者发现问题却无处上报”的真实一次：制品缺失导致必须自写桥接才能完成安装（见同目录 `反馈-MCP制品不可下载-2026-11-24.md`）。如果有反馈通道，这条问题会在安装失败当场进入商店，作者和审核都不需要等使用者绕出来。
