# 反馈：带制品的版本能查能出计划，但取制品一律 `VERSION_UNAVAILABLE: 制品文件不可读`

- 反馈日期：2026-11-24
- 反馈来源：按商店 MCP 标准流程下载两个技能包（要求只下载、不安装）
- 涉及商品：`luxi.paper-arts@4.3.0`、`luxi.gov-unified-writer@3.2.0`；同一时段 `luxi.qc-lifecycle-manager@3.2.0` 同现象
- 客户端/平台：DeepSeek Harness，darwin-arm64
- 性质：已发布制品的路径解析缺陷（数据与启动位置耦合），影响所有带制品的种类

## 一、现象

1. 目录侧全部正常：`search`、`list_versions`、`resolve`、`describe`、`install_plan` 都返回成功。
2. 取制品全部失败，传不传 `platform` 都一样：

   ```
   artifact(id=luxi.paper-arts, version=4.3.0)                → VERSION_UNAVAILABLE: 制品文件不可读
   artifact(id=luxi.paper-arts, version=4.3.0, platform=any)  → 同上
   artifact(id=luxi.gov-unified-writer, version=3.2.0)        → 同上
   artifact(id=luxi.qc-lifecycle-manager, version=3.2.0)      → 同上
   ```

3. 但 `install_plan` 能正常给出下载步骤：

   ```json
   {"op": "download",
    "url": "http://10.37.87.25:8084/v1/artifacts/luxi.paper-arts/4.3.0",
    "sha256": "ee3eafcb5be98bf3640e8f38447399114c20487322c0f774feefefdc07a9e16a",
    "dest": "${WORK}/luxi.paper-arts/4.3.0.zip"}
   ```

4. 按计划直接 GET 该地址：`HTTP/1.1 400`，正文还是同一句（`HEAD` 同样 400）：

   ```json
   {"rule": "VERSION_UNAVAILABLE", "message": "制品文件不可读"}
   ```

也就是说：说明在、计划在、sha256 在，**缺的只是"文件在服务端读得到"**。

## 二、定位

三处代码，链路很短：

| 位置 | 行为 |
|---|---|
| `store/catalog.py:715-722` `artifact()` | `path.read_bytes()` 抛 `OSError` → 报 `VERSION_UNAVAILABLE: 制品文件不可读` |
| `store/http_api.py:788-791` `_send_artifact()` | `archive.stat()` 抛 `OSError` → 报同一句 |
| `store/catalog.py:698-699` `artifact_file()` | 对 `skill`/`knowledge`/`plugin`/`mcp+skill` 直接 `Path(row["artifact_path"])`，不做任何解析 |

而落库的路径是**相对启动目录**的：

- `store/catalog.py:164-177` `_archive_release()`：`dest = self.blob_dir / "releases" / <id> / <version>.zip`，返回 `str(dest)` 写进 `releases.artifact_path`；
- `store/cli/__init__.py:63`：`--blobs` 默认取 `QILIN_BLOBS`，否则用相对路径 `var/blobs`；
- 本机库实测该列：

  ```
  luxi.paper-arts/4.3.0           → var/blobs/releases/luxi.paper-arts/4.3.0.zip
  luxi.gov-unified-writer/3.2.0   → var/blobs/releases/luxi.gov-unified-writer/3.2.0.zip
  ```

于是 DB 里存的是"发布那次进程 cwd 下的相对路径"。只要对外服务进程的 cwd 不是仓库根——systemd 的 `WorkingDirectory`、launchd、docker 的 workdir，或数据目录从 `./data` 迁到 `QILIN_BLOBS=/var/lib/qilin/blobs` 之后——`Path(...)` 就指向不存在的位置，`stat()`/`read_bytes()` 抛 `OSError`。

旁证：发布时 `_verify_artifact()`（`catalog.py:149-162`）已经逐字节比对过文件与 sha256，所以"文件不存在"只可能在发布**之后**才发生：迁移、换机、换启动目录。制品本身没坏。

## 三、影响

- **所有带制品的品类都下不了**：`skill`、`knowledge`、`plugin`、`mcp+skill`。`runtime` 的 `release_assets.path` 同样由 `blob_dir` 拼出、同样落相对路径（本机 `submissions.artifact_path` 也是 `var/blobs/...` 形态），一旦有 runtime 商品会踩同一个坑。
- **症状误导排查**：`VERSION_UNAVAILABLE` 与"版本不存在 / 被下架"共用同一个规则号和文案。客户端只能看到"版本不可用"，会去换版本、重试、怀疑商品没了，真正原因却是服务端磁盘路径。
- **失败点被推到安装最后一步**：`install_plan` 照常返回 `download` + `sha256`，安装器会忠实地去拉一个必然 400 的地址。
- **`artifact` 工具做了多余的重活**：`mcp_api.py:375-379` 为了返回 `sha256` 调 `store.artifact()`，而它是**整包读进内存**（32MiB 上限）；DB 的 `artifact_sha256` 本来就有。结果是"只问下载地址"也强依赖磁盘可读，大包还白读一遍，和工具描述"不返回文件正文"也不一致。
- **本次实际后果**：商店侧下载不了，只能从本机仓库 `var/blobs/releases/...` 直接取原件；两个包的 sha256 与 `install_plan` 下发值逐字节一致——进一步说明坏的是取文件入口，不是制品。

## 四、建议（供评审，不指定实现）

1. **存逻辑键，不存物理路径。** `releases.artifact_path` 改存 `releases/<id>/<version>.zip`（相对 `blob_dir`），读取时用当前 `blob_dir` 拼；或启动时把历史记录统一重写成绝对路径。取其一，迁移才自洽。
2. **错误语义分开。** 版本不存在继续 `VERSION_UNAVAILABLE` / 404；"有记录但文件读不到"用新规则（如 `ARTIFACT_MISSING`）+ 503，并把 `id@version` 与期望路径写进服务端日志（不回给未授权调用方）。
3. **发送时再校验一次。** `_send_artifact()` 现在不算摘要；建议流式计算 sha256，与 DB 不一致就中止并报 `ARTIFACT_MISSING`，坏包不下发。
4. **`artifact` 工具不读正文。** 直接返回 `_artifact_url(...)` + DB 的 `artifact_sha256`，最多做一次 `stat()` 存在性检查。
5. **健康检查纳入制品可读性。** `/api/health`（`base.py:258-271`）现在只判断 `blobs` 目录"存在且可写"；建议加对 `releases` 的抽样可读检查，缺文件即 `degraded`，让探针能发现这类事故。
6. **启动自检 + 修数据命令。** `serve` 启动时扫描 `releases` / `release_assets`，日志给出"记录 N 条 / 可读 M 条 / 缺失前若干"；配套 `doctor --repair-paths`，按当前 `blob_dir` 重新对齐旧记录。
7. **迁移验收加一步。** backup/restore 后随机取一个版本 `artifact` 并比对 sha256，作为恢复流程的固定冒烟项（`store/backup.py` 已有的 manifest 可直接复用）。

## 五、可验收的判定

1. 任一已发布版本 `artifact` 返回 200、字节数正确，`sha256` 与 `install_plan` 一致。
2. 换一套数据目录与启动目录（模拟迁移）后，不改 DB 也能下载成功——证明路径不再绑 cwd。
3. 人为移走一个 zip：`artifact` 返回新规则 + 503，`/api/health` 变 `degraded`，客户端不会误判成"版本没了"。
4. 人为改一个字节：下载被拒并报校验类规则，不发出损坏包。
5. `kind=mcp` 且"种类不做制品分发"的报错（`这个产品没有可下载的制品`）与新规则区分开，不再共用 `VERSION_UNAVAILABLE` 同一句。
