# 五项待定设计：密钥、MCP 依赖、知识包、元数据、插件包

日期：2026-11-16。范围：只回答设计问题，不改代码。事实以本机安装的 DeepSeek Harness（下称 DSH）文档与本仓库代码为准；DSH 侧引用的文件都在安装包内（`dsh/node_modules/@deepseek-ai/dsh-*/README.md` 与 `dsh-agent-preset/skills/dsh-doc/references/*.md`）。

先给结论，再逐条说明。

| # | 问题 | 结论 | 落点 | 波次 |
|---|---|---|---|---|
| 1 | 技能带 KEY 的范式 | 密钥不是技能资产，是**凭据引用**。harness 用凭据缝取，技能只读环境变量；**不写进技能目录** | 规格 4.1/4.8、`get_spec` 新资源、`install_plan.need_secret` | W2 |

## 1. 技能携带 KEY：把「密钥」从产品里赶出去

### 1.1 现状

规格第 4.1 节要求 `secrets[]` 只写名字和说明，安装步骤里有一条 `need_secret`。代码里这条链是断的：

- `plan.py:133` 生成 `{op: need_secret, name, description}`；
- `installer.py:201 _need_secret` 只打印一行「需要环境变量 X」，没有获取、没有保存、没有绑定；
- 规格第 6 节说「写入客户端自己的密钥存储」，但没说「客户端」是谁、存储在哪、技能怎么读。

于是现实里的做法会退化成你说的那种：让 AI 用 `ask` 问用户，然后把值写进 `SKILL.md` 或 `references/`。这条路有三个问题：

1. **会被商店拒绝**。`validate.py` 的 `SECRET_FILE`/`SECRET_PATTERN` 会命中，提交直接退回。
2. **技能目录变成密钥仓库**。复制、分享、备份、升级都会带走明文；这正是规格第 4.8 节要禁的事。
3. **换 KEY 要改文件**。密钥轮换变成一次文件编辑，而且改完还进不了版本库。

### 1.2 DSH 已经有的机制

- `@deepseek-ai/dsh-credentials`：凭据按名字引用（POSIX 标识符），提供 `set/unset/resolve/describe`；**值不进配置、不进 UI、不进诊断**；本地 provider 落盘在 `$DSH_HOME/.env`，并叠加进程环境；每次操作重新解析，所以轮换立即生效。
- `@deepseek-ai/dsh-authorization`：为「通过一次与人的对话拿到凭据」提供的接缝。
- `@deepseek-ai/dsh-tool-ask-user`：`ask_user_question`。
- `@deepseek-ai/dsh-mcp-client`：`expandTemplates: true` 时，`env`/`headers` 里可写 `${credential:REF}`，缺值进入 `waiting-credentials` 并等待更新。

也就是说：**「问用户」和「保存」在 DSH 里是两个已有的、分开的能力**，不需要技能自己发明文件格式。

### 1.3 建议范式（三层，缺一不可）

**声明层（商店清单）**：只声明名字与获取方式，永远不出现值。

```json
"secrets": [
  {
    "name": "GS_API_KEY",
    "description": "国信行情接口密钥",
    "required": true,
    "acquire": "prompt",
    "hint": "在内部网关申请，形如 sk-…",
    "verify": ["python3", "-c", "import os,sys; sys.exit(0 if os.environ.get('GS_API_KEY') else 1)"]
  }
]
```

- `acquire`：`prompt`（安装时问一次）、`env`（用户自己导出）、`oauth`（走授权流程）、`none`（公开占位，不建议）。
- `verify` 可选，客户端在本机执行；商店服务器永远不执行它。
- 值出现在 `secrets[]` 里仍是 `SECRET_PATTERN`。

**获取层（harness）**：由安装器或插件的授权流程完成，不由技能写文件。

- 首选：`ctx.authorization` 的流程（插件实现）→ `ctx.credentials.set(credentialRef(name), value)`。
- 次选：用户自己在设置里填，或在自己 shell 里 `export`。
- 兜底：`ask_user_question` 问一次，由**调用方**（harness）存，不交给技能。

**使用层（技能/服务）**：只读环境变量。

- 技能脚本：`os.environ["GS_API_KEY"]`，找不到就给出明确错误，不提示「把密钥写进文件」。
- MCP：`env: {GS_API_KEY: !!js process.env.GS_API_KEY}`，或 `expandTemplates` 下的 `${credential:GS_API_KEY}`。

### 1.4 安装计划怎么改

把现在这条只在终端打印的步骤，改成可被客户端执行的「绑定」：

```json
{ "op": "need_secret", "name": "GS_API_KEY", "description": "国信行情接口密钥",
  "acquire": "prompt", "hint": "…", "required": true }
```

`install_plan` 不携带值，也不指定客户端路径。客户端把它翻译成自己的凭据存储：DSH 是 `ctx.credentials` 或 `$DSH_HOME/.env`；其他客户端是各自的密钥串。

**推荐器与技能正文的分工**：`SKILL.md` 只写「运行前需要环境变量 X；没有就停下来，让用户通过 harness 的凭据设置提供」，**不写「把密钥写入 references/xxx.md」**。`get_spec` 增发一份 `qilin://spec/secrets`，把这条写成硬约定。

### 1.5 验收

1. 一个声明两个 secret 的技能包：`install_plan` 产生两条 `need_secret`，不含值。
2. 未配置时技能退出并提示「用 harness 设置提供」；配置后同一次会话内可用。
3. 包内任何文件都不出现密钥；`store validate` 无 `SECRET_*`。
4. 轮换后不需要改包、不需要重新安装。

## 2. MCP 依赖与规范遵循

### 2.0 先分清：商品目录 ≠ 交付格式（2026-11-16 修订）

上一版把「MCP 商品」和「配置文件怎么落到 DSH」混在一起，是需要纠正的。两层要分开：

- **目录层（商店）**：商品是一份被审核过的连接声明——id、版本、作者、说明、鉴权方式、工具面、适用客户端、审核记录。`kind=mcp` 的商品就是这份声明，作者提交的也**只是**这份声明（JSON），不需要提交任何 bundle。
- **适配层（客户端）**：安装到某台机器时，把这份声明渲染成该客户端认识的格式。DSH 的格式恰好是一个配置式 bundle；别的客户端可能是 `.mcp.json`、一段 YAML、一条 CLI 命令。渲染物由商品清单生成，不单独版本化，也不进商店目录。

因此：

1. **不会丧失外部 MCP 服务清单。** 清单是主，bundle 是清单的落盘形式。把 bundle 当商品反而会丧失清单：商品会变成 DSH 专用，换一个客户端就得重做一件商品。
2. **「本身就是一段 JSON」是对的**，但这段 JSON 不是随手贴的 URL。它是契约：连接方式、鉴权声明、工具面快照、版本与变更。商店的价值是可发现、可审核、可复现、可回滚，不是 JSON 本身。
3. **配置式 bundle 机制上是 bundle，商品上不是插件。** 详见 5.2。

### 2.1 现状与差距

商店的 `mcp` 块只有 `transport`、`url`、`command`、`args`；`install_plan` 生成抽象的 `mcp_add`；`installer._mcp_add` 把步骤原样写成一个 JSON 文件。对照 DSH 的 `dsh-mcp-client` 配置面，缺的不只是字段：

| DSH 配置 | 商店现状 | 影响 |
|---|---|---|
| `serverName`（`[A-Za-z0-9_-]{1,32}`，同作用域唯一） | 无，安装器用 `id` 当文件名 | 工具名前缀 `mcp__<server>__<tool>` 无法预先确定 |
| `env`（stdio，合并到擦洗后的环境） | 无 | 无法表达「哪个密钥注入哪个变量」 |
| `headers`（http，可含 `${credential:REF}`） | 无 | 远程 MCP 的鉴权无处声明 |
| `startupTimeoutMs` / `toolCallTimeoutMs` | 无 | 慢服务没有上限 |
| `reconnect` / `failOnStartupError` | 无 | 启动失败策略不可声明 |
| `expandTemplates` | 无 | 凭据模板无法启用 |

还有三处协议层面的差距：

1. **版本协商**：DSH 客户端默认选 2026-07-28，商店 `PROTOCOL_VERSIONS` 最高只到 2025-06-18，每次连接都会降到 2025-06-18。降级本身是规范的正常行为，但商店应至少声明自己能支持的最高版本，并在核实新版本语义后再加，不要凭印象加。
2. **工具错误**：商店的 JSON-RPC 错误走 `-32001`，工具级失败没有用 `isError: true` 的 `CallToolResult`。
3. **分页**：`tools/list`、`resources/list` 一次全量返回。规范允许无 cursor 的单页，规模小没问题；工具变多时要加分页。

### 2.2 建议的清单扩展

`mcp` 块补到能直接生成一份 DSH 配置：

```json
"mcp": {
  "transport": "streamable-http",
  "url": "https://mcp.internal/market",
  "server_name": "gs-market",
  "headers": { "Authorization": "Bearer ${credential:GS_API_KEY}" },
  "startup_timeout_ms": 20000,
  "tool_call_timeout_ms": 60000,
  "reconnect": { "enabled": true, "max_attempts": 10 },
  "fail_on_startup_error": false
}
```

- `server_name` 可选。默认由 `id` 转写：小写、`[a-z0-9_-]`、把 `.` 换成 `-`、总长 ≤32；写成非法值报 `MCP_SERVER_NAME`。
- `headers` 的值只允许两种：静态非敏感字符串，或 `${credential:NAME}`；出现其他插值或疑似密钥报 `SECRET_PATTERN`。
- `env` 的键用 `ENV_NAME`，值必须是 `secrets[].name` 里的名字，否则报 `SECRET_UNDECLARED`。

### 2.3 依赖怎么表达

把 `depends.mcp` 拆成两种来源，避免「商店内产品」和「外部服务」混在一个字段里：

```json
"depends": {
  "mcp": [
    { "source": "store", "id": "luxi.gs-market", "version": ">=1.2.0" },
    { "source": "external", "server_name": "company-ocr", "transport": "streamable-http",
      "url": "https://ocr.internal/mcp", "expected_tools": ["ocr_image"] }
  ]
}
```

- `source: store`：递归展开成具体步骤，带环检测（`DEP_CYCLE`）；不再发 `ensure_product` 标记，避免外部安装器重复安装。
- `source: external`：商店不托管，只做声明与可达性检查（`initialize` + `tools/list`，10 秒超时）；检查通过才允许发布。`expected_tools` 只用于 `approve` 时对照，不参与运行。
- 安装顺序固定：`runtime` → `external` 的 `ensure_bin` → `depends.mcp`（按拓扑）→ 本包 `mcp_add` → 技能解压 → `need_secret` → `verify`。
- 同一个 MCP 被两个依赖引用时只装一次（按 `(source, id|server_name, version)` 去重）。

### 2.4 适配格式：DSH 侧生成配置式 bundle（商品仍是 `kind=mcp`）

DSH 里接一个 MCP，标准做法是一个**配置式 bundle**：`package.json` 声明 `dsh.bundle.patch`，patch 插入 `@deepseek-ai/dsh-mcp-client`，带 `serverName`、`transport`、`url`（或 `command`/`args`/`env`）。安装走 Plugins 的「添加插件」，或 `plugin_manager`。

但这不改变商品形态：

- 作者提交的仍是连接声明，`kind` 仍是 `mcp`；
- `install_plan` 仍输出抽象 `mcp_add`，不含任何 DSH 路径与 patch 文本；
- **DSH 适配器**（客户端侧的一小段渲染逻辑，或安装器的 `bundle_render` 步骤）把 `mcp_add` 渲染成 `$DSH_HOME/plugins/staging/<id>/<version>/` 下的配置式 bundle，再提示用户在 Plugins 里添加。不自动安装——`install_bundle` 需要用户批准，安装器没有这个权限，也不该有。
- 渲染物不单独版本化、不进搜索、不参与审核；同一份商品换客户端只需换渲染器。

一句话：**bundle 是 DSH 的安装单位，不是商店的商品分类。**

### 2.5 商店自己作为 MCP server

- 补 `serverName` 无关（服务器没有这个名字），但 `initialize` 返回的 `serverInfo.version` 应与 `store.__version__` 一致，而不是写死 `0.1.0`。
- 工具级失败用 `isError: true`，JSON-RPC 错误只用于协议层错误（-32600/-32601/-32602/-32002）。
- `instructions` 控制在 32KiB 内（DSH 客户端的上限），超了会被拒绝连接。
- 若要声明 2026-07-28：先按该版本规范核对 `initialize`、工具结果、资源读取的变化，再加进 `PROTOCOL_VERSIONS`，并补一条协商测试。

### 2.6 外部 MCP 商品在目录里记录什么

既然商品是「声明」而不是 bundle，声明里就应该有审核和发现需要的东西：

- `server_name`：工具名前缀的来源，装到 DSH 后是 `mcp__<server_name>__<tool>`。
- `auth`：`none` / `bearer` / `oauth`，以及 header 名与凭据引用名；URL 里不允许带值。
- `tools_snapshot`：审核时抓一次 `tools/list`，存工具名与输入 schema 的 sha256（不存正文），作为发布时的事实基线。
- `expected_tools`：作者声明的工具面。发布后重探发现与快照不一致，可以提示「工具面已变」，但不在 v1 自动下架。
- 这些字段让「一段 JSON」变成可审核、可对比、可告警的契约，而不是一张 URL 便条。

### 2.7 验收

1. 一个 `kind=mcp` 的产品，安装后 DSH 的工具列表出现 `mcp__<serverName>__<tool>`。
2. 两个 `depends.mcp`（一个店内、一个外部）按顺序出现，环检测报 `DEP_CYCLE`。
3. 缺凭据时连接进入 `waiting-credentials`，补齐后自动连上，不重启。
4. 商店 `initialize` 的 `instructions` 字节数小于 32768。

## 3. 知识包：从「能闭合」到「可检查的契约」

> 2026-11-16 补：详细范式已单独成文——`docs/知识包范式设计-2026-11-16.md`（词表 kv/1、题头 schema、链接与命名、迁移映射、校验规则变更）。本节保留决策摘要。

### 3.1 现状

已有：根目录 Markdown、YAML 题头（type/status/created/updated/tags）、`[[篇名]]` 闭合、`knowledge.entry`、可选 `taxonomy` 与 `knowledge_map`。规范通过 `get_spec` 与 `qilin://spec/knowledge` 下发。

三个不足：

1. **规范只有散文**。harness 读到的是给人看的段落，没有机器可读的 schema 或清单。
2. **解析器太窄**。`knowledge._block` 要求文件以精确的 `---\n` 开头，`_fields` 只认「键: 值 + 缩进列表」。实测：UTF-8 BOM、CRLF、`tags: [a, b]`、`description: >` 都会误判。这些是常见写法，不是刁钻输入。
3. **校验入口分裂**。MCP 的 `validate` 只收清单，看不到笔记；完整校验只能在本机跑 `store validate <目录>`。这个分工是对的（不把正文塞进对话），但规范里没写清「什么时候必须跑 CLI」。

### 3.2 建议：三层规范资源

| 资源 | 形态 | 谁读 |
|---|---|---|
| `qilin://spec/knowledge` | 现有散文 | 人、模型 |
| `qilin://schema/knowledge` | JSON Schema：清单 `knowledge` 块 + 每篇题头 | 工具、校验器、IDE |
| `qilin://checklist/knowledge` | 逐条可勾选清单（10–15 条） | 模型在打包前自检 |
| `qilin://example/knowledge` | 一个最小合格包（3 篇笔记 + 清单） | 模型对照 |

`get_spec` 的返回从 `{name, text}` 扩为 `{name, text, version, hash}`。`hash` 是正文的 sha256；规范一改，hash 就变，harness 可以据此决定要不要重读。资源 URI 不变，避免破坏现有客户端。

### 3.3 建议加严的规则

| 项 | 规则 | 规则 id |
|---|---|---|
| 入口 | `knowledge.entry` 必须存在，且该篇 `type` 为 `map_of_content` | `NOTE_ENTRY` |
| 日期 | `updated >= created`，都是合法日期 | `NOTE_FRONTMATTER` |
| 标签 | 数组，1–12 项，每项 ≤32 字 | `NOTE_FRONTMATTER` |
| 编码 | UTF-8；容忍 BOM 与 CRLF（读入时归一，不报错） | — |
| 大小 | 单篇 ≤256KiB；整包 ≤8MiB | `NOTE_FILE` |
| 链接 | 闭合；允许自指；不允许指向 `manifest.json` | `NOTE_LINK` |
| 子目录 | 仍然禁止 | `NOTE_FILE` |

其中「入口必须是 `map_of_content`」是新增的硬约束，理由是：知识包要给 AI 一个明确的读起点的结构，而不是一篇普通笔记。

### 3.4 解析器要修的四件事

1. 开头 `lstrip("\ufeff")`，`splitlines()` 之后按行处理（同时吃掉 CRLF）。
2. `tags: [a, b]` 这类流式数组按数组接受（一项一项剥引号）。
3. `key: |` / `key: >` 折叠标量：至少不把它判成「值不合法」；`description` 这类可选字段按原文接受。
4. `---` 结束行允许 `---` 后带空格；题头内部出现 `---` 时以第一个结束行为准（现有行为，保留）。

### 3.5 harness 侧怎么用

规范里写死这条顺序，不要靠模型自由发挥：

1. `get_spec(name="knowledge")` 或读 `qilin://spec/knowledge`；
2. 读 `qilin://schema/knowledge` 与 `qilin://checklist/knowledge`；
3. 写笔记与清单；
4. 在本机跑 `store validate <目录>`（这是**唯一**读到全文的校验）；
5. 通过后 `store submit <目录>`；
6. 失败就按 `rule` 与 `path` 改，不要改规则。

### 3.6 验收

用一份真实笔记库（例如某个项目的 20–50 篇笔记）走完整链路：常见写法（BOM、CRLF、流式 tags、折叠 description）不误报；入口、链接、日期错误有明确 `rule` 与 `path`；`store submit` 进入 `pending`。

## 4. 资产元数据：核心字段封闭 + `meta` 扩展

### 4.1 现状

核心字段已经够描述「这是什么、怎么装」：id/version/kind/title/summary/description/changes/author/platforms/clients/depends/secrets/invoke。缺的是「怎么被找到、被谁用、能不能信」：

- 没有标签与分类，搜索只能靠 `summary` 子串；
- 没有许可证、主页、图标；
- 没有语言、成熟度、适用人群；
- 门户卡片只有一句话和 id。

### 4.2 建议的两层模型

**核心层**（必填，封闭，参与校验）：现状不变。

**扩展层**（可选，命名空间化）：

```json
"meta": {
  "tags": ["公文", "质检", "国信"],
  "categories": ["writing"],
  "license": "internal-only",
  "homepage": "https://…",
  "language": ["zh-CN"],
  "audience": ["analyst", "reviewer"],
  "maturity": "stable",
  "security_level": "internal",
  "support": "team@example.internal",
  "icon": "assets/icon.svg"
}
```

约束：

- `categories` 用固定枚举，与货架分类同源，不自由填。
- `tags` 受控词表 + 自由词：自由词最多 8 个，每个 ≤16 字；受控词表由 `registry.py` 维护。
- `license`、`maturity`、`security_level` 都是枚举，不允许长句。
- `icon` 是包内相对路径，仅允许 SVG/PNG，≤256KiB；安装时不解压到磁盘之外。
- `meta` 进 `public_view` 白名单；审核单原样保留。
- 元数据变更随版本不可变（与现有 `VERSION_IMMUTABLE` 一致）；不新增「只改元数据」的绿色通道，避免第二次审核绕过。

### 4.3 明确不做

- **不把「可信」做进元数据**。`verified`、`signed`、`official` 这类字段不是作者能声明的；信任来自签名与审核记录，属于另一个维度。
- **不允许 HTML/Markdown 片段进入 `meta`**。渲染在客户端做，商店只存结构化值。
- **不引入自由分类**。分类是用来收敛导航的，自由分类等于没有分类。

### 4.4 对搜索与门户的影响

- `search` 增加对 `tags`、`categories`、`meta.language` 的匹配；`kind`/`client`/`platform` 过滤不变。
- 门户卡片增加 tags 行；详情页在七组之外加一组「元数据」，只展示，不可编辑。
- 这些字段都不影响安装计划。

### 4.5 验收

一个带 3 个 tag、1 个 category、许可证与图标的包：`describe` 返回 `meta`；搜索 tag 能命中；门户显示图标与标签；`meta` 里写 HTML 被 `META_INVALID` 拒绝。

## 5. 插件包：先界定，再决定要不要加

### 5.1 DSH 的事实

- **插件就是一个 bundle 包**：`package.json` 里声明 `dsh.bundle.patch`，patch 插入插件行；可以是 Host 插件（`index.js`）、Client 插件（UI）、或**配置式**（没有代码，只插入一条 MCP 连接）。
- 安装走 `plugin_manager` 的 `install_bundle`，以本地目录为 target；**影响整个 profile**，重启后仍在。
- 插件代码跑在 Harness 进程内，权限与 Harness 相同。
- **MCP 是进程/服务边界**：DSH 通过 `dsh-mcp-client` 连接，工具以 `mcp__<serverName>__<tool>` 注册。连接本身也是用一个配置式 bundle 装进去的。
- **技能是目录 + SKILL.md**，由 skill provider 加载，模型按需读取；不是 npm 包，也不在 Harness 进程内执行代码。

### 5.2 怎么界定

按**执行边界**分，不按打包格式分。先把最容易混的一处说清：

- **机制层面**：配置式 bundle 确实是 DSH 的 bundle，和插件走同一个安装入口。这一点你说得对。
- **商品层面**：配置式 bundle 不含任何代码，只是 MCP 连接的一种落盘形式；把它算成插件商品，等于把「连的东西」和「跑在你身体里的东西」压成同一类，审核标准会一起失守。
- 所以 `kind=plugin` 只留给**分发可执行代码**（Host/Client 扩展、生命周期、UI 注入）的商品；MCP 商品的安装产物即使是个 bundle，也仍然属于 `kind=mcp`。

| 维度 | 技能包 | MCP | 插件包 |
|---|---|---|---|
| 跑在哪 | Agent 上下文 + 本机脚本 | 独立进程/远端服务 | Harness 进程内（Host/Client） |
| 装什么 | 解压到技能目录 | 一条连接（配置式 bundle） | npm 包 + patch 行 |
| 权限 | 与 Agent 相同 | 独立进程，网络面自控 | 与 Harness 相同（最高） |
| 坏了的后果 | 一次任务失败 | 该 server 工具不可用 | 整个 profile 或 UI 受影响 |
| 审核重点 | 提示词、脚本、密钥 | 协议、工具面、鉴权 | 代码、依赖、生命周期、UI 注入 |

一句话：**技能是「读的东西」，MCP 是「连的东西」，插件是「跑在你身体里的东西」。**

### 5.3 要不要加 `kind=plugin`

技术上可以加，但**不建议 v1 开放**。三个理由：

1. **权限模型不匹配**。当前审核只看清单、文件清单与文本差异，没有代码审核能力；插件可以读凭据、改 UI、发网络请求。
2. **安装链路不匹配**。商店安装器只能解包与放文件；`install_bundle` 是 Harness 的工具，需要用户批准，商店不能代劳。插件包的安装必然多一步人工确认，这没问题，但要在规格里写清。
3. **供应链面变大**。npm 依赖、install scripts、build 产物、版本锁定，每一项都是新的审核负担。当前项目连 CI 都还没有，先开这个口子风险不对称。

建议分三步：

1. **现在**：`kind=mcp` 商品不变，DSH 适配器把 `mcp_add` 渲染成配置式 bundle（见 2.4）。这一步不引入任何可执行代码，却能覆盖「装一个 MCP 到 DSH」的全部场景。
2. **预留**：`KINDS` 加 `plugin`，但校验器对 `kind=plugin` 直接返回 `PLUGIN_NOT_SUPPORTED`（error），并在 `get_spec` 里写清原因与计划。这样以后开口子不需要改 `spec_version`，也不会有人误以为已支持。
3. **设计 spike（不实现）**：单独一份 `docs/插件包设计.md`，至少回答：
   - 包形态：`package.json` + `cordis.patch.yml` + `index.js`/`client.js` + locale + icon；
   - 审核清单：无 install script、依赖白名单、静态扫描、`files` 白名单；
   - 安装 op：`plugin_stage`（下载、校验、解包到 `$DSH_HOME/plugins/staging/`）+ 人工确认 `install_bundle`；
   - 回滚：禁用 → 卸载 → 保留上一版；
   - 签名与来源：谁能发、怎么验、审核记录怎么留。

### 5.4 如果一定要在近期加，最小形态

- `kind=plugin`，必填 `plugin.bundle`（patch 路径）、`plugin.entry`、`plugin.files`；
- 制品是 `npm pack` 的 tgz；安装器只解包到 staging，不执行任何脚本；
- `clients` 只允许 `deepseek-harness`；`platforms` 写具体平台，不允许 `any`；
- 审核强制人工代码审；商店不执行 `npm install`，也不接受带 `scripts` 的包；
- 商店侧只做「托管 + 审核 + 分发」，不做「替你装」。

### 5.5 验收（预留态）

- 提交 `kind=plugin` 得到 `PLUGIN_NOT_SUPPORTED`，`get_spec(name="plugin")` 返回原因与计划；
- `KINDS` 与 schema 的枚举同步，不会出现「schema 认、校验器不认」；
- 已发布的技能与 MCP 不受影响。
