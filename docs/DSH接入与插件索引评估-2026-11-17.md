# DSH 接入与插件索引源评估

日期：2026-11-17。依据：本机 DSH `@deepseek-ai/dsh` 0.2.2-rc.3 的安装包文档与类型定义，不凭印象。

## 0. 结论

1. **“插件索引源”这个想法本身成立，但不能直接用商店现在的 zip 制品做。** DSH 的插件索引格式 1 只接受两种安装来源：npm（`name@version`）或 Git（commit + path）。商店现在的插件制品是 zip，DSH 索引无法安装它。
2. **对“部门私有、规模不大”的现状，不建议先做索引源。** 要做索引，等于再建一条 npm 私有 registry 或 Git 镜像发布通道；收益是 DSH Discover 里能直接看到，代价是多一套发布、凭据、审计和回滚。
3. **更合适的 DSH 接入是“两个配置式 bundle + 一个只读 MCP 端点”**：
   - `qilin-store`：不带 KEY，只读/安装用，给普通用户。
   - `qilin-manage`：带 `${credential:QILIN_STORE_KEY}`，发布/审核用，只给作者和审核。
   - 两者都只是 `@deepseek-ai/dsh-mcp-client` 的配置，不含可执行代码；不占 `kind=plugin`。
4. **KEY MCP 已经能支撑商店运作**；独立只读 MCP 的意义是“让安装不需要把管理 KEY 发给每个用户”，不是新增一套商店协议。
5. **下载是否必须 KEY，是当前唯一需要先定的策略。** 现在 `/v1/artifacts`、MCP `artifact`、`install_plan` 都是匿名的；如果改成 KEY 才能下载，只读 MCP 也必须带 reader KEY 或改用签名 URL。

## 1. DSH 插件索引到底认什么

`@deepseek-ai/dsh-plugin-market` 的 README 说明：索引是用户配置的 URL，Host 读取后用 `@deepseek-ai/dsh-plugin-market-index` 校验；安装走 `pluginManager.installBundle`。

`@deepseek-ai/dsh-plugin-market-index/src/types.ts` 的 `MarketSource` 只有：

```ts
type MarketSource =
  | { type: 'npm'; registry?: string }
  | { type: 'git'; url: string; commit: string; path?: string }
```

每个版本还需要：

- `version`：精确 SemVer
- `publishTimestamp`：Unix 秒
- `source`：上面的 npm 或 git
- `engines.dsh`：DSH 版本范围
- 插件级：`name`（npm 包名）、`title`/`description`（本地化）、`icon`、`author`、`homepage`、`repository`、`metadata`、`versions`

也就是说：

- 索引里的 `name@version` 会交给 pnpm 安装；Git 条目会按 commit 拉取。
- **没有“HTTP zip 制品 URL”这种来源。**
- 索引是未签名的，DSH 的已知限制明确写“index content is the index's claim”；它不校验发布者/审核状态。
- 安装前 DSH 还会做兼容性检查（`engines.dsh`）和安装状态标注，但**不经过商店的 `plugin_stage` / `plugin_confirm` / 审核清单**。

## 2. 如果坚持做索引，需要补什么

| 方案 | 需要做的事 | 代价 |
|---|---|---|
| A. 私有 npm registry | 每个已审核插件发布成 npm 包；索引写 `name@version` + `registry`；DSH 用 pnpm 装 | 多一套 Verdaccio/私有 registry、发布凭据、版本回滚、包内容与 zip 的一致性 |
| B. Git 镜像 | 每个插件推到 Git，索引写 commit + path；DSH 按 commit 拉 | 多一套仓库/权限/提交策略；每次发布要打 commit；私有仓库需要 DSH 侧 Git 凭据 |
| C. 自定义 DSH Host 插件 | 不写索引，写一个调用商店 HTTP API 的插件，自己实现查询/安装 | 要维护 Host 插件代码；与商店 MCP 功能重复；插件在 DSH 进程内运行，权限更大 |
| D. 只做配置式 MCP bundle | 不做索引；用户安装一个只读 MCP 连接，商店 MCP 负责查询/install_plan/artifact | 不能在 DSH Discover 里直接看到插件列表；但链路最短、审核与 staging 都在商店 |

**对部门私有、小规模：D 最划算。** A/B 的收益主要是“Discover 里直接看到”，但你们已经有商店门户和 MCP 搜索，重复建设明显。C 比 MCP 更重，不建议。

## 3. 两个 MCP 配置怎么分

当前 MCP 的可见性已经按角色分：

- 匿名：`get_spec`、`search`、`list_versions`、`resolve`、`describe`、`install_plan`、`artifact`
- 作者：加 `validate`、`begin_submit`、`finish_submit`、修订、我的提交
- 审核：加 `list_reviews`、`get_review`、`review_plugin`、`approve`、`reject`、`unpublish`、`transfer_namespace`、`list_audit`

所以同一个 `/mcp` 端点，**不带 Authorization 就是只读**，带 KEY 就是管理。可以不改后端，直接做两个配置式 bundle。

### 3.1 `qilin-store`（只读，给普通用户）

```yaml
- insert:
    - id: mcp-qilin-store
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: qilin-store
        transport: streamable-http
        url: https://qilin.example.com/mcp
        failOnStartupError: true
        reconnect:
          enabled: true
```

工具名：`mcp__qilin-store__search`、`install_plan`、`artifact` 等。

### 3.2 `qilin-manage`（管理，给作者/审核）

```yaml
- insert:
    - id: mcp-qilin-manage
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: qilin-manage
        transport: streamable-http
        url: https://qilin.example.com/mcp
        expandTemplates: true
        headers:
          Authorization: !!js '`Bearer ${process.env.QILIN_STORE_KEY}`'
        failOnStartupError: true
```

也可以用 DSH 的凭据引用 `${credential:QILIN_STORE_KEY}`（`expandTemplates: true`），把 KEY 放进 DSH 凭据存储，而不是环境变量。配置式 bundle 本身不含 KEY。

工具名：`mcp__qilin-manage__begin_submit`、`approve` 等。

### 3.3 要更进一步：只读端点

如果担心“只读 bundle 被误配 KEY”，可以加 `/mcp/read`：

- 忽略 `Authorization`，固定匿名 principal；
- 只返回 `PUBLIC` 工具；
- 管理仍走 `/mcp`。

这是后端小改动，收益是语义清晰；但不是必须。当前匿名/带 KEY 的行为已经正确。

## 4. 下载与 KEY 的策略选择

现状（需要明确）：

- `/v1/artifacts/<id>/<version>` 是公开的，不要求登录；
- MCP `artifact` 是公开工具；
- `install_plan` 是公开的；
- 门户文案说“页面下载须先登录”，但服务端制品地址不校验 KEY。

这和“下载需要 KEY”有冲突。三种选择：

| 方案 | 行为 | 适用 |
|---|---|---|
| A. 保持公开 | 内网/反代边界内可下载；只读 MCP 可直接安装 | 部门私有网络，最简单 |
| B. reader KEY | 新增 reader 角色；`artifact`/`install_plan` 要求 KEY；只读 MCP 配置 reader KEY | 需要“下载也算受控”，但每个用户要有 KEY |
| C. 签名 URL | `install_plan`/`artifact` 生成短 TTL 签名下载地址；生成时校验 KEY，安装器下载不带头 | 对外暴露、又不想给安装器配 KEY |

**建议：内网 v1 用 A，公网/跨部门用 C。** B 会让“只读 MCP 不需要 KEY”的便利消失；C 在下载层做短期授权，最适合“管理要 KEY、安装要方便”。

## 5. 建议的推进顺序

### P0（现在，不改协议）

1. 做两个配置式 bundle：`qilin-store`（只读）与 `qilin-manage`（KEY）。
2. 在 `integrations/` 放模板，写清楚 `serverName`、URL、credential 引用；不发布到商店 `kind=plugin`（它们没有代码）。
3. 门户「连接」页并列展示两种配置：普通用户只读、作者/审核管理。

### P1（决定下载策略后）

- 选 A：只读 MCP 直接可用；文档写明内网边界。
- 选 B：加 reader 角色与工具可见性；只读 bundle 配 reader KEY。
- 选 C：加签名 URL；`install_plan`/`artifact` 生成时校验 KEY，下载地址短 TTL。

### P2（只有确实需要 Discover 才做）

- 选 A（npm）：私有 registry + 每个插件的 npm 发布流水线 + 索引生成器（format 1）。
- 选 B（Git）：插件 Git 镜像 + commit 固定 + 索引生成器。
- 无论哪种，索引只列已审核/已发布版本；索引本身不替代商店审核。

## 7. 结论一句话

**索引源不是“不建议做”，而是“现在的 zip 制品做不了；要做先改发布形态”。对部门私有、小规模，先用两个配置式 MCP bundle 把 DSH 的安装路径打通；索引源等确有 Discover 需求、并愿意维护 npm/Git 发布通道时再做。**
