## 0. 结论摘要

1. **设计边界是清醒的，这一点比多数同类项目做得好。**「商店是菜市场，不是厨房」不是口号：不执行安装、不存产品密钥值、安装计划以数据（op 列表）形式交给客户端，代码里都守住了。五类产品、封闭词表、三段上传、单份校验器四处复用，都是有意识的设计。
2. **架构的主要风险不在「分几层」，而在「一个类装下了整个领域」。** `Store` 一个类 1994 行、97 个方法、82 处 SQL，同时承担存储迁移、认证、账号、提交、审核、货架、安装计划七类职责；一把全局锁套住所有数据库访问与慢哈希。
3. **功能主链路是通的，但「集市身份」还没成立。** 提交→审核→发布→安装计划→参考安装器都能跑；缺的是规格 §7.2 已经写明的命名空间归属（同一 `id` 归首个发布者），以及一处被忽略的状态守卫（`reject` 不校验状态）。
4. **工程化是当前最大的短板，且与代码质量无关。** 没有 git 仓库、没有 `.gitignore`、没有 CI/格式/类型门禁；`pip install` 之后门户页面和 schema 不会进包；运行时数据库、WAL、上传制品、`__pycache__` 全在源码树里。
5. **完整性约七成。** 规格 §17.3 的 13 项里 12 项已做或有明确部分实现，第 13 项（登记表不再充当资产名单）未做；阶段 5/6 的「真实包验收」没有做，所以这套代码还没有被一次真实上架检验过。
6. **判断：可内部试用（127.0.0.1，知根知底的人），不宜直接对外交付。** 按第 8 节四个波次推进，约 20–30 人日可到「可交付给第一位外部用户」。

## 2. 架构评估

### 2.1 做对了的地方

| 判断 | 证据 | 为什么重要 |
|---|---|---|
| 边界写进了代码，不只是文档 | `service.py` 无任何执行安装、无产品密钥读取；`plan.py` 只生成步骤 | 商店被攻破时，损失上限是「目录与制品」，不是「用户电脑」 |
| 大文件不经过 MCP 参数 | `begin_submit` 只收 `byte_size`，制品走 `PUT /v1/uploads/{id}`（`http_api.py:334`） | 避免把 32MiB 塞进模型上下文，这是实践里最容易走偏的一条 |
| 安装计划是数据，op 封闭 | `plan.py:OPS` 8 个 op；`installer.py:83` 未知 op 立即停 | 客户端可审计、可干跑、可换实现 |
| 校验器只有一份 | `validator/validate.py` 被 CLI、HTTP、MCP、`submit_client` 共用 | 不会出现「门户能过、MCP 不过」 |
| 路径安全收成一份 | `safety.py` 的 `check_relative`/`safe_join`，四处共用 | 原来四处各写一套，其中一处完全没有检查（`_keep_assets`） |
| 公开视图白名单 | `service.py:1801 public_view` | 作者多写一个未知顶层字段，不会自动公开 |
| 反例扫描干净 | 全仓无 `except:`、无 `eval/exec`、无 `shell=True`、门户 `innerHTML` 0 次 | 说明代码习惯稳定，不是碰巧 |

### 2.2 结构问题

**（1）`Store` 是上帝类，且职责按「方法相邻」而不是「变化原因」聚在一起。**

七类职责混在一个类里：建表与迁移（54–199）、认证与账号（201–379、643–1074）、提交与上传（381–642、1088–1315）、审核发布（428–486、1316–1362）、货架与安装计划（487–535、1364–1453）、视图与差异（1749–1994）。后果不是「行数多」本身，而是：

- 任何一处新增规则都要改同一个文件，评审面和冲突面最大；
- 测试只能用 `store._db` 直接改库（`tests/test_deployment.py:39` 等 9 处），因为领域对象没有可注入的边界；
- 锁与事务的粒度被迫全局统一，无法按用例收窄。

**（2）分层有一处是反的。**

`accounts.py:9` `from store.service import StoreError`，而 `service.py` 只能在函数体内延迟 import `accounts`（`service.py:287`、`737`、`763`）来掩盖循环。正确方向是 `StoreError`（以及 `Principal`）下沉到一个不依赖任何东西的 `errors.py`/`domain.py`，`accounts` 与 `service` 都向上依赖它。

**（3）两个协议层各自长、且能力面不对称。**

HTTP 22 个分支、MCP 18 个工具，错误形状两套（`http_api.py:351 _fail` 与 `mcp_api.py:392 _fail`）。更实际的问题是**能力不对齐**：MCP 有 `withdraw` 与 `unpublish`，HTTP/门户没有对应路由——审核员在门户里下不了架，必须去 MCP 客户端；发布者也不能在门户撤回。这与规格 §15「我的提交」的语义不完整。

**（4）错误模型不成体系。**

61 个规则 id 以字符串字面量散落在 8 个模块，没有一张 `rule → HTTP 状态 → 用户文案` 的表。直接后果：

- HTTP 只有 400 与 403 两档，没有 401/404/409，客户端无法按语义分支；
- `VERSION_UNAVAILABLE` 同时表示「没这条提交」「没这个用户」「没这个版本」「没这个地址」（`service.py:358/436/1135/182`），排障时无法区分；
- 500 响应把异常类名和原文回给调用方（`http_api.py:191/332/349`），`OSError` 的路径、`sqlite3` 的语句会外泄；
- `INTERNAL`、`STATE_UNBOUND` 两个实际在用的码不在规格第 12 节的表里。

### 2.3 并发与一致性：当前最脆弱的一段

这一节单独写，因为它是「小规模能用、一上量就出事」的典型。

**并发模型的实际语义**：`ThreadingHTTPServer` + 单个 `sqlite3` 连接（`check_same_thread=False`）+ 一把 `RLock`（`service.py:68`）。所有公开方法都 `with self._lock`，因此**实际并发度是 1**。更关键的是锁内的东西：

| 锁内动作 | 位置 | 实测/推算代价 |
|---|---|---|
| KEY 认证的逐行 scrypt（旧行兜底） | `service.py:280` 起 | 每次认证约 33ms |
| 注册时逐行 scrypt 查重 | `service.py:347 _reject_reused_key` | 第 N 个账号注册 ≈ N×33ms，且全程持锁 |
| JWKS 拉取（`urlopen`，5s 超时） | `identity.py:_keys` ← `service.py:218` | 任何 `a.b.c` 形状且长度 >256 的 Bearer 都能触发 |
| 打包、写 zip、搬资产 | `service.py:393`、`1518` | 随包体线性增长 |

实测口径：KEY 鉴权约 33ms/次，一次 MCP 工具调用做两次认证约 66ms，单进程上限约 15–30 RPS。这个量级对百人内网够用，但它同时意味着**一个慢请求会挡住全站**——包括只读的货架页。

**JWKS 在锁内**是最值得先修的一条：令牌形状检查（`token.count(".") == 2 and len > 256`）在验签之前，攻击者不需要有效令牌，只要发一个长点号串，就能让全店排队等 5 秒公钥超时。文档「还留着的风险」里没有这一条。

**事务与状态**：

- 全仓没有 `rollback`，也没有 `BEGIN IMMEDIATE`。`sqlite3` 默认在第一条 DML 时开隐式事务，异常时不回滚——下一个请求的 `commit` 会把半截写入带进去。`revise`（`service.py:584`）先 `DELETE submission_assets`、再删旧 zip、再重新打包校验，中途失败就留下「库指向已删文件」。
- 状态校验散在 6 处（`435/597/1134/1166/1231/1308`），没有迁移表。`reject` 完全没有状态守卫（`service.py:471`）：已发布的提交可以被改成 `rejected`（发布行还在，状态记录失真）。`withdraw` 之后没有后续清理路径，`expired` 只有 `prune` 会写。
- `finish_submit` 是两段锁（`service.py:1149`）：第一段取行，出锁做 URL 探测，第二段提交。并发两次 `finish` 时，第二个会正常报「不在等待制品」，这可以接受；但两段之间没有幂等标记，重试语义靠状态字符串推断。
- 迁移框架是 `PRAGMA table_info` + `ALTER TABLE` + 启动时全表 `UPDATE` 回填（`service.py:173`），没有 schema 版本号。表结构是 `CREATE TABLE IF NOT EXISTS`，新增非账号表时没有迁移路径。

### 2.4 可维护性数字

- 单文件 1994 行、97 个方法；`_public`/`_private` 成对包装占 42×2 个方法——这是「锁在入口、逻辑在内部」的写法，本身合理，但让类的表面积翻倍，也让「谁该调哪个」变成隐性约定。
- 魔法数字：`_MAX_BYTES=32MiB`、`_MAX_BODY≈43.7MiB`、`MAX_UNPACKED=64MiB`、72 小时、7 天会话、10 分钟 state，全部是模块常量，未配置化（文档已记录，属实）。
- 日志：只有鉴权失败、拒绝、未捕获异常三类，无请求 ID、无耗时、无访问日志。长期运行只能排「出了什么事」，排不了「慢在哪」。

## 3. 功能设计评估

### 3.1 域模型：概念一致，但状态机是隐式的

规格 §3 的状态图很清楚（`uploading → pending → published/rejected`，`published → unpublished`），代码里也有全部状态。缺的是一张**显式的迁移表**：谁能从哪个状态到哪个状态、失败后落到哪。现在这层知识分散在 6 个 `if row["status"] != ...` 里，其中一处漏了（`reject`）。

建议的形态（不用引库，一张字面量表即可）：

```python
TRANSITIONS = {
    ("uploading", "finish_ok"): "pending",
    ("uploading", "finish_retryable"): "uploading",
    ("uploading", "finish_bad"): "rejected",
    ("pending", "approve"): "published",
    ("pending", "reject"): "rejected",
    ("pending", "withdraw"): "withdrawn",
    ("rejected", "revise"): "pending",
    ("published", "unpublish"): "unpublished",
}
```

所有写状态的地方只调 `_transition(row, event)`；非法迁移统一抛 `VERSION_UNAVAILABLE`（或新码 `STATE_INVALID`），并补上现有 6 处漏检。

### 3.2 身份：三种凭据 + 一个未落地的归属规则

`principal_from_token`（`service.py:218`）按顺序试四种凭据：会话 cookie、hub 登录、商店 KEY、枢纽 JWT，最后回落到测试用 `principals` 表。这个顺序本身有讲究（快的在前），但带来两个问题：

1. **语义不统一**：枢纽用户的 `Principal.id` 是令牌 `sub`，商店用户是 `u_xxx`；审计表 `actor` 混着两种。建议在 `Principal` 上加 `source`，审计里写 `source:id`。
2. **没有商品归属**：规格 §7.2 明确「同一 `id` 已由别的发布者发布 → 拒绝」，`_prepare`（`service.py:1455`）只挡了 `VERSION_IMMUTABLE`，没查归属。任何 publisher 都能给别人的 `id` 发新版本，`author.publisher_id` 会被改写成提交者。这是功能设计层面的缺口，不是实现 bug——文档也标了未做，但它决定「集市」能不能立起来。

**首个账号自动成为 admin**（`service.py:697`）是合理的本机引导方式，但在公网部署下是「谁先注册谁当管理员」。建议保留默认行为，同时支持 `QILIN_BOOTSTRAP_TOKEN`：设了就要求带令牌才能创建第一个 admin，或者由 CLI 预置。

### 3.3 上传/审核/安装链路：这是最扎实的一段

- 三段上传（begin / PUT / finish）职责清楚，`finish` 把 URL 探测放在锁外（`service.py:1149` 起），文档里那一条「不再占锁」是真实实现。
- `validate`（只读清单）与 `finish_submit`（读包内文件、跨文件核对）的分层，正是规格想要的：AI 工具第一次就能拿到快速反馈，不必把 32MiB 塞进参数。
- 安装计划 8 个 op、依赖递归、环检测（`plan.py:94`）、`resolve` 只选版本不默认最新、`install_plan` 强制精确版本——这一整套在同类项目里少见，是对的。

这一段的缺口都在细节，见 5.2 与第 6 节：安装器的解压没有体积上限、`ensure_product` 语义双解、`mcp_add` 把注入路径写进产物。

### 3.4 审计与运维：只写不读

`audit` 表记录了 12 类动作（注册、发 KEY、提交、发布、退回、下架、改角色……），但**没有任何读取入口**：没有 API、没有门户页、没有导出。出了争议只能 `sqlite3` 手查。这不是「功能没做完」，而是「有数据没有出口」，成本很低（一个只读接口 + 一个列表页），收益很高。

同样属于「有基础设施没有出口」的：`/api/health` 存在但 README 未提；`prune_stale_uploads` 只有启动与 `begin_submit` 两个触发点。

### 3.5 门户：功能齐、结构单薄

1978 行单文件（CSS 206 行 + JS 1362 行），7 个视图，48 个函数，1 个 `fetch` 封装。安全习惯是好的：`innerHTML` 0 次、`textContent` 50 次、无 `eval`。但它没有模块、没有构建、没有 DOM 测试，门户测试全是「HTML 里有没有这个中文串」（`tests/test_portal.py:39-63` 约 20 条 `assertIn`）。这意味着**改 JS 逻辑不会被任何测试拦住**。

短期不必上框架。建议只做三件事：按视图拆成 `<script>` 段或独立文件（仍免构建，用 ES module + `type="module"`）；把 `state` 收成一个可替换对象；把「渲染」函数与「请求」函数分开，以便将来用 Node 直接跑渲染函数。

## 4. 工程化评估

### 4.1 P0：没有版本控制，且运行数据在源码树里

- `git status` → 不是仓库。这一条单独列为 P0，不是洁癖：这个项目的文档密度（三份长文档、逐条记录「已做/未做」）说明它值得有历史；而现在任何一次误改、误删都无法回退，也无法做 code review。
- 根目录 `qilin.db`、`qilin.db-wal`、`qilin.db-shm`、`var/qilin.db`、`qilin-blobs/`、`var/blobs/`、`__pycache__/`、`.pytest_cache/` 都在树里。其中 `.db` 有真实账号与会话、`blobs` 有真实制品。**建议不是「删掉」，而是移出 + 轮换**：把库和制品移到 `var/`（或独立目录），把 `var/` 全部进 `.gitignore`；已存在的这一份因为是真实工作库，迁移后应作废其中的口令与 KEY，再重新签发。

### 4.2 P1：打包不成立

`pyproject.toml` 只有 11 行，没有 `[build-system]`，没有 `package-data`。实际后果：

- `qilin-portal.html` 在仓库根、不在 `store/` 包内 → `pip install` 后 `http_api.PORTAL` 指向不存在的位置，`/` 直接 404；
- `store/spec/store.schema.json` 在包目录内但没有 package-data → 不进 wheel；
- 门户 CSS 与两枚 SVG 来自仓库外的 `../LUCY-DESIGN`（`http_api.py:26`）→ 换台机器克隆就掉样式，`tests/test_portal.py:65` 同时失败。

三种修法里推荐第一种：把门户与静态资源移进 `store/portal/`，用 `importlib.resources` 读取，`pyproject` 加 `[tool.setuptools.package-data]`；`store.spec` 同样处理；`LUCY-DESIGN` 的三份文件（`tokens.css`、`qilin.svg`、`luxi-lab-gold.svg`）复制进 `store/portal/assets/` 并注明来源。

### 4.3 P1：没有门禁

无 CI、无 Makefile/tox、无 ruff/black/mypy/coverage 配置、无 pre-commit。依赖只有 `cryptography>=42`，未锁版本、无 lock 文件。考虑到项目本来就用 pytest 和 `unittest`，最低成本的组合是：

- `ruff check` + `ruff format --check`（零配置起步）；
- `pytest -q` + `coverage`（先不设门槛，只出报告）；
- 一条 `.github/workflows/ci.yml`，Python 3.11/3.12/3.13 三档矩阵——顺带验证 `requires-python >=3.11` 是否真的成立（本机只跑过 3.14）。

`cryptography` 只在枢纽验签用（`identity.py:13`）。建议改成 **optional extra**：`[project.optional-dependencies] hub = ["cryptography>=42"]`，并在 `identity.py` 里延迟 import，取不到时给出「未安装枢纽支持」的明确错误。这样 README 的「运行时只用标准库」就变成事实，而不是需要读者自己去发现的反例。

### 4.4 测试：形态健康，边界缺三类

**健康的地方**：148 个用例、46 个 subtest，62% 走真实 HTTP + 临时 SQLite，不 mock 核心；`test_hardening.py` 专门测路径穿越、zip 冲突、`tree_dest`；`test_deployment.py` 专门测指纹回填、残留清理、Host 形状、Cookie 属性。这是「按缺陷类型建测试文件」的思路，比按模块铺更有效。

**缺的三类**：

1. **并发 0**：唯一涉线程的用例（`tests/test_service.py:137-162`）只证明 `finish_submit` 不占锁，没有并发提交、并发 approve、并发注册。第 2.3 节的问题都不会被现有测试发现。
2. **非法状态迁移 0**：`reject` 把 `published` 改成 `rejected` 这种，没有任何用例。
3. **MCP 协议边界只覆盖 1/5**：只有 `-32002` 有断言；`-32600`、`-32601`（`mcp_api.py:242`）、notification 返回 `None`、batch、缺参数都没测。

另外，61 个规则 id 里约 25 个没有被任何测试引用（`ACCOUNT_DISABLED`、`MCP_TRANSPORT`、`SKILL_INVOKE`、`PLATFORM_*` 系列、`NOTE_ENTRY` 等）。不必追求逐个覆盖，但「每个 kind 至少一条负例」应当补齐。

**慢**：33 秒里大头是 scrypt（每次注册/登录/认证）与每次造 RSA-2048 密钥（`tests/tokens.py`）。可以在测试里把 `_SCRYPT_N` 降为 `2**10`（用环境变量或 monkeypatch），把时间压到 5 秒内，为 CI 铺路。

### 4.5 文档：最大资产，但有四处漂移

这份项目的文档纪律（只增补、逐条写「没做」、把「刻意保留的差距」写清楚）在同类项目里是罕见的，应当保持。但「文档即契约」在这里已经开始失效：

| 文档声明 | 代码实际 | 判断 |
|---|---|---|
| README：「运行时只用 Python 标准库」 | `identity.py:13` 用 `cryptography` | 漂移（按 4.3 修） |
| 规格 §10：`server/` 用 FastAPI，分四包 | 单包 `store/`，`http.server` | 漂移。建议改规格：stdlib 选择是合理的，不该被文档否定 |
| 规格 §9：`release_platforms`、`validation_report_json`、`client_caps` | `release_assets`、`validation_json`，无 `client_caps` | 漂移（命名与表结构） |
| 规格 §10：「请求体超过 32MiB 拒收」 | `_MAX_BYTES` 32MiB，`_MAX_BODY`≈43.7MiB | 措辞不精确：32MiB 是制品上限，正文上限另算 |

**根因**：文档是唯一契约，没有测试绑定它。建议加一条低成本约束——把规格里的关键断言写成测试名或测试注释（例如 `test_public_view_hides_unknown_top_level_fields`），让「文档说做了」变成「测试证明做了」。

## 7. 改进建议

按「先止血、再收口、后补齐」排序。每条都给了验收口径，便于逐项打勾。

### 7.1 立即做（约 3–4 人日）

1. **建版本基线**：`git init`；写 `.gitignore`（`*.db*`、`var/`、`qilin-blobs/`、`__pycache__/`、`.pytest_cache/`、`.env`）；把现有库与制品移到 `var/` 后**轮换口令与所有 KEY**，旧库归档不删。
   - 验收：`git status` 干净；`git log` 有首个提交；仓库里 `grep -r "password_hash\|key_hash"` 只出现在代码与文档。
2. **JWKS 出锁**：把 `identity.principal()` 的调用移到锁外；`_keys` 加单飞（同一时刻只允许一个刷新，其余等待结果）与负缓存（失败 30s 内不再重试）。
   - 验收：一个新的并发用例——一个长点号串请求与一个货架请求并发，货架响应 < 200ms。
3. **500 不外泄**：对外只回 `rule` + 一个随机 `trace_id`，栈与原文只进日志；`auth_failure` 的 path 去掉查询串，或只记 path 的前 64 字符并脱敏 `code=`/`state=`。
   - 验收：构造一次内部异常，响应体不含文件路径与异常类名；日志里 `code=` 已脱敏。
4. **解压统一**：`installer._unpack` 改为调用 `blobs.safe_extract`（自带 `MAX_UNPACKED` 与路径守卫），`_download` 改为分块读 + 上限；`service._finish_checked` 捕获 `OSError` 并记 `CHECKSUM`。
   - 验收：安装器对 100MiB zip 拒绝；`x`/`x/y` 冲突的包在服务端得到 `CHECKSUM`（非 500）且状态为 `rejected`。

### 7.2 结构收口（约 8–10 人日）

5. **拆 `Store`**（建议按变化原因切，不按行数切）：
   - `store/errors.py`：`StoreError`、`Principal`、规则注册表；
   - `store/storage.py`：连接、迁移（带 `schema_version` 表）、事务上下文；
   - `store/auth.py`：会话/KEY/枢纽、`principal_from_token`；
   - `store/submissions.py`：begin/PUT/finish/revise/state machine；
   - `store/releases.py`：审核、发布、下架、货架、安装计划；
   - `store/views.py`：`public_view`/`review_view`/diff/预览；
   - `service.py` 退化为门面（facade），保留现有公开方法名，HTTP/MCP 不动。
   - 验收：`service.py` < 200 行；`accounts.py` 不再 import `service`；现有 148 个测试零改动通过。
6. **并发与事务**：每线程一个连接（`threading.local` + WAL + `busy_timeout`）；多步写统一 `with self.tx():`（`BEGIN IMMEDIATE`，异常 `rollback`）；blob 用「临时文件 → 校验 → `os.replace` → 单事务改库」。
   - 验收：新增并发用例（两个 publisher 同时 begin/finish，一个 admin 同时 approve 另一条），无「库指向已删文件」，无 500。
7. **错误注册表**：`RULES = {rule: (http_status, user_message)}`，`StoreError` 携带 rule；HTTP 从表里取状态码；补 401/404/409。
   - 验收：`VERSION_UNAVAILABLE` 按场景拆成 `SUBMISSION_NOT_FOUND`/`RELEASE_NOT_FOUND`/`ROUTE_NOT_FOUND`（或保留一码但带 `detail`），客户端可分支。

9. **门禁**：`ruff` + `pytest` + `coverage`；GitHub Actions 三档 Python 矩阵；测试里把 `_SCRYPT_N` 降到 `2**10`。
   - 验收：CI 绿；全套测试 < 10s；覆盖率报告可下载。

### 7.3 功能补齐（约 10–12 人日）

- **M2（W1 末）**：可安装、可回滚、可协作——换台机器 `pip install` 能起，CI 能拦回归。
- **M3（W2 末）**：集市语义成立——商品有主、状态可信、审计可查。
- **M4（W3 末）**：可交付——真实包跑通全链路，有备份恢复手册。

**排期建议**：W0 与 W1 不要并行改同一批文件；W1 的拆类期间冻结行为变更；W2 的登记表退场单独一个 PR；W3 之前不做任何界面美化。

## 9. 不建议做的事

以下与规格一致，评估后仍然认为不该做，列出来是为了防止后续被「顺手加上」：

- **不引入 Web 框架**。当前 `http.server` 够用，换框架的收益不抵迁移成本；需要的是路由表与中间件式的错误处理，不是框架。
- **不做多实例**。单进程单库配合「停进程冷备」是当前规模的正解；要做多实例，先有外部制品存储与并发写方案，别先改代码。
- **不做服务端执行安装**。这是边界，不是缺陷。
- **不做产品密钥保管、不做调用网关、不做语义搜索**（规格 §11 已列）。
- **不把知识树真的落盘**，除非先答清演进规划 §3 的五个问题。

## 10. 风险与判断

1. **最大风险是「文档事实源分裂」。** 规格、演进规划、工程记录三份文档互相引用，已经出现断链（§14.5）、重复（§17.3 第 13 项）、以及两套互斥的登记表模型。建议定一条规矩：**规格是唯一的规范性文本，演进规划只记录「为什么改」与「改的顺序」，工程记录只记录「已发生了什么」**；任何一条规格断言，在代码里有对应测试才算落实。
2. **第二大风险是「只有一个人知道为什么」。** 工程记录写得足够细，这是缓解；但它记录的是「做了什么」，不是「为什么这么选」。建议在 `docs/` 下补一份 `决策记录.md`（ADR 风格，每条 10 行以内）：为什么不用 FastAPI、为什么密钥不由用户设、为什么安装计划是数据。这比再写一万字过程记录更有复用价值。
3. **第三是规模假设不清。** 当前设计按「内网、几十人、几百个包」优化；代码里没有分页、没有索引、搜索是全表 `json.loads`。这个假设应当写进规格，并在 W2 至少给货架加 `LIMIT/OFFSET` 与 `(kind, published_at)` 索引——成本很低，能推迟一次重构。
4. **代码质量本身不是问题。** 无裸 `except`、无 `eval`、无 shell 注入、路径守卫统一、公开视图白名单、148 个测试——这些说明作者（或作者与 AI 的协作方式）是稳的。真正拖后腿的是工程底座（版本控制、打包、CI）和三个「还没被真实使用检验过」的假设（并发、真实包、归属）。
