## 2026-11-11 身份改接枢纽，商店 MCP 按流式 HTTP 握手

栖林不再在第一次启动时打印作者密钥和管理密钥。那样做等于人工分配：谁拿到那一行字，谁就是作者或审核。

现在密钥只接受枢纽用户管理已经签发的访问令牌。

- 应用 id：`lucy-qilin`
- 角色：`publisher`（上传到待审核）、`admin`（发布、退回、下架）。两个都有时按 `admin`
- 没有这两个角色的人可以看货架，不能上传
- 验签：`RS256`，`iss` 为枢纽地址，`aud` 为 `lucy-qilin`，`typ` 为 `access`
- 公钥：`{QILIN_HUB_ORIGIN}/.well-known/jwks.json`，缓存 `jwks-cache.json`
- 启动：`store serve --hub-origin http://枢纽地址`。不配地址时不创建本地密钥，匿名仍可看货架
- 枢纽侧：`app/seed_data.py` 增加栖林；已有库用迁移 `0003_seed_lucy_qilin`

商店 MCP 仍是 `POST /mcp`。补上了客户端真正会发的握手：`initialize` 按对方协议版本回答，`ping`，`notifications/initialized` 回 202，`initialize` 带 `Mcp-Session-Id`。只要事件流、不要 JSON 时，响应用 `text/event-stream`。`GET /mcp` 是 405。令牌签不上时，MCP 回 JSON-RPC 错误，不把人当成匿名。

门户顶栏改成「枢纽令牌」，货架加上搜索、分类和在架数量。卡片写类型、版本、摘要、产品 id、平台、AI 工具和作者。安装说明仍然只展示。

还没做：

- 枢纽访问令牌大约 10 分钟过期。栖林不把它换成自己的长期密钥，过期要回用户管理再领
- 没有做门户跳转登录（`/auth/callback` 换 code）。人把领到的令牌贴进门户或 MCP 配置
- 登出回调只核销 `typ=logout`，没有服务端会话可清。已发出的访问令牌等到自己过期
- 阶段 6：真实技能还没迁入
- 测试夹具里的 `create_principal` 仍往本地表写密钥，只给未接枢纽的测试用。`store serve` 不走这条路

规格改动写在 `agent-store-design.md` 第 2 节和文首修订行。规则 id 增加 `IDENTITY_INVALID`、`IDENTITY_UNCONFIGURED`。

## 2026-11-11 用户自己创建 KEY

上一节把入口收成枢纽令牌之后，日常还是要人去别处领一串令牌。这一节改成汇流那种做法：用户名、显示名、本人设置的 KEY。

- 第一位是审核，之后自己注册的是作者
- 门户登录后只留会话，KEY 不留在页面上
- 商店 MCP 的 Bearer 就是这把 KEY
- 审核可以改角色、停用，不能看见或代设 KEY
- 换 KEY 后旧的立即失效；和别人重复则 `KEY_TAKEN`
- 产品卡片改成完整的一句话，详情先写说明，调用和依赖不再倒 JSON
- 枢纽令牌仍然可以验，但只作为更长的 Bearer，不代替创建 KEY

规则 id：`USERNAME_INVALID` `USERNAME_TAKEN` `NAME_INVALID` `KEY_INVALID` `KEY_MISMATCH` `KEY_TAKEN` `ACCOUNT_DISABLED` `LAST_ADMIN`。

## 2026-11-11 一把随机 KEY，和连接页

上一节让人自己设置 KEY。这一节改掉：创建账号时商店生成一把，每人同时只有一把，不能在请求里自己带一把（`KEY_INVALID`）。

- 资料是用户名、姓名、昵称、部门、岗位。昵称出现在顶栏和登录名单。用户名创建后不改
- 明文和商店 MCP 配置只在创建、以及本人重新生成的那一次响应里出现。重新生成作废原来的那一把，并清掉旧会话
- 左栏「连接」把这段配置交给 AI 工具。之后再打开，只说明已经生成，不再显示明文
- 管理员仍然看不见、不能代设别人的 KEY
- 详情里，版本表的适用平台是作者写的。`any` 显示为「任意平台」。旁边的「装到这台电脑」不是创建时保存的：安装说明不接受 `any`，所以要选一台具体的电脑，这个选择不写回产品

枢纽长令牌仍可验，不代替这把 KEY。

## 2026-11-11 口令与用户管理分开

上一节把登录和商店 MCP 收成同一把 KEY。创建页因此没有口令，必填和复杂度也看不出来。用户管理藏在登录之后，页面上像没有。

这一节拆开：

- 口令自己设置，用来登录。10 到 64 位，须含小写、大写和数字，不能包含用户名，首尾不能是空格。两次不一致则 `PASSWORD_MISMATCH`，规则不满足则 `PASSWORD_INVALID`
- 创建页标出必填和选填。口令规则写在框下面，随输入显示已满足或未满足
- KEY 仍由商店生成一把，只给商店 MCP。拿 KEY 当口令登录会被拒绝。改口令不换 KEY
- 「用户管理」单独成页。审核能改角色、停用，能看见部门和岗位。看不见口令，看不见 KEY，不能代设。作者打开只看到不能管理
- 上架单里规格要求的字段同样标成必填，空着不能提交

规则 id 增加 `PASSWORD_INVALID`、`PASSWORD_MISMATCH`。

## 2026-11-11 枢纽跳转登录，令牌快过期就续

上一节让地址打不开的提交可以再交。这一节做第 17.3 节的第 5 条。

- 枢纽把人带到 `GET /auth/callback?code=&state=`。栖林用 `QILIN_HUB_SECRET` 签名去换访问令牌，验签后写自己的会话。地址上不出现令牌
- 枢纽若给了刷新令牌，只留在 `hub_logins`，接口不回显。访问令牌剩不到一分钟时再换一次，旧的作废。换不到就结束这次会话
- 枢纽这次没给刷新令牌，会话就停在该访问令牌的过期时间。人从枢纽再进，不用把令牌贴进来
- 这条会话不产生商店 KEY。日常仍是口令和 KEY。没配应用密钥则 `IDENTITY_UNCONFIGURED`
- 枢纽的登出回调清掉这个人的跳转会话

## 2026-11-12 安全修复、目录上传与知识树预留

上一节把技能目录的改造划在本工程之外。这一节只改商店自己。

- 打包和提交时丢掉 `.DS_Store`、`._*`、`__MACOSX`、版本库和缓存目录，以及 `.storeignore` 里的路径。`.storeignore` 本身不进包。压缩包目标若在待打包目录里面，不把这个 zip 再打进去

- 没有把在架知识包改到分类目录，也没有改技能仓库里的登记目录

## 2026-11-12 部署与运维口径：KEY 定位、残留上传、对外地址、日志

上一节改的是打包、解压和校验。这一节处理上线之后才会遇到的问题：请求变多时的比对成本、上传半途而废留下的文件、放在反向代理后面的对外地址，以及出问题时看不到任何记录。功能行为不变。

- 账号表加 `key_prefix`，存 KEY 的 sha256 前 16 位十六进制，并建索引。认证先用它定位候选行，再对候选行做一次 scrypt。旧库里没有指纹的行落到兜底分支，仍然全表比对；比对成功后顺手回填指纹，下次就走索引。存量 KEY 不需要重新签发
- `accounts` 表新增列的迁移写在 `_migrate_accounts` 里，和已有列一样用 `PRAGMA table_info` 判断后再 `ALTER TABLE`
- 停在 `status='uploading'` 的提交，超过 72 小时由 `prune_stale_uploads` 标成 `expired`，并删掉 `artifact_path` 指向的文件。启动时跑一次，每次 `begin_submit` 也跑一次。不另起后台线程
- `serve` 增加 `--public-base`，也可读 `QILIN_PUBLIC_BASE`。对外地址的来源顺序是：显式配置，其次 `X-Forwarded-Proto` 与 `Host`，最后本地监听地址。没有配置时，反代部署会生成 http 的安装计划，这一点写在帮助文字里
- `Host` 头只接受字母数字和 `.-_:[]`，长度不超过 255。形状不合法就退回本地监听地址，不把它拼进安装计划
- 会话 Cookie 在对外地址是 https 时带 `Secure`。原来分隔符后少一个空格，`HttpOnly` 会和上一个属性粘在一起，一并修掉
- HTTP 正文上限和制品上限分开：`_MAX_BODY` 比 `_MAX_BYTES` 多出 base64 的膨胀量和 1MiB 余量。原先把两者写成同一个数，32MiB 的制品经 base64 之后必然超限，等于这类包永远交不上来。制品本身仍按 `_MAX_BYTES` 卡
- 正文里的文件用 `base64.b64decode(..., validate=True)`。原先非法字符被静默丢弃，截断的上传会当成成功
- 读不到制品文件时抛 `VERSION_UNAVAILABLE`，不再让 `FileNotFoundError` 冒到 500
- 新增 `store/diagnostics.py`。鉴权失败按 warning 记规则名，不记口令和 KEY；未预料的异常带 `exc_info` 记栈。`--log-level` 或 `QILIN_LOG_LEVEL` 调整级别，默认 `WARNING`，输出到 stderr。仍然不记访问日志
- 新增 `tests/test_deployment.py`：指纹回填、旧行仍可认证、残留上传清理、对外地址优先级、`Host` 形状、Cookie 属性、正文上限、base64 严格解码、制品缺失。全套 128 个用例通过

## 2026-11-13 跳转登录的 state 与登录请求绑在同一个浏览器上

上一节处理部署与运维。这一节补审计里唯一还没动的安全项：回调的 `state` 只检查了非空，没有和这次登录请求绑在一起。

先说清一件事：枢纽自己发起的跳转，`state` 由枢纽决定，商店无从预知，光校验形状没有意义。要让 `state` 真正可比对，跳转必须由商店发起。

- 新增 `--hub-authorize`（或 `QILIN_HUB_AUTHORIZE`），值是授权页地址，可含 `{state}`、`{redirect_uri}`、`{app_id}` 三个占位。商店只做字面替换，不解析模板，也不假设授权页的参数名
- `redirect_uri` 由商店自己的对外地址推出，不接受从请求里读的值。否则就成了让外部指定令牌落到哪
- 新增 `GET /auth/start`。签发一次性 state，写进名为 `qilin_hub_state` 的 Cookie，`Path=/auth`、`HttpOnly`、`SameSite=Lax`，https 下带 `Secure`，十分钟有效，然后带人去授权页
- `/auth/callback` 用 `compare_digest` 比对 Cookie 与地址里的 state。对不上、或根本没有这只 Cookie 时拒绝，规则仍是 `IDENTITY_INVALID`，并且在换令牌之前就拒绝
- 通过后在一次响应里下发两条 `Set-Cookie`：建立会话、把 state 清成 `Max-Age=0`。为此响应附加头从字典改成 `(name, value)` 列表，HTTP 允许同名头重复出现
- 没配 `--hub-authorize` 时，`/auth/start` 回 `IDENTITY_UNCONFIGURED`；回调仍照旧可用，但每次都记一条 `STATE_UNBOUND` 警告。这是刻意保留的差距，不把「未绑定」当成「已修好」
- `GET /v1/identity` 多一个 `hub_start` 字段。门户据此决定显不显示「实验室账号登录」。按钮走整页跳转（`window.location.assign`），不用 `fetch`——state 要在同一次响应里写进 Cookie，`fetch` 拿不到
- 新增 `tests/test_hub_state.py`：签发与跳转地址、state 每次不同、Cookie 与 state 一致时建立会话、无 Cookie 拒绝、state 不符拒绝、长度不同不抛异常、无模板时 start 不可用且回调记 `STATE_UNBOUND`、模板替换与编码。全套 144 个用例通过

没做的部分：枢纽授权页的真实地址与参数名不在本仓库，模板只能由部署者填。`--hub-authorize` 的值是可信输入，商店没有校验它是不是 http/https，也没有校验域名——这一条写在演进规划的「还留着的风险」里。

并发那一条没有动：`key_prefix` 只降低了逐行 scrypt 的成本，鉴权仍在全局锁内，多线程服务实际仍是一请求一排队。改它要动 SQLite 连接在锁外复用的前提，不混在这一轮。

## 2026-11-13 MCP 的 GET 不能再写出第二条状态行

AI 工具连 `http://127.0.0.1:8787/mcp` 时，除了 POST，还会 GET 一次，用来打开单独的 SSE。商店不提供这条流，按规范回 405，并带 `Allow: POST`。

原先把 `Allow` 放进字典。`_empty` 在状态行已经放进缓冲之后才拆这个字典，拆失败后异常处理又写了一条 400。两次状态行连在同一个头块里。Python 的 `urllib` 仍把第一条当成 405，Go 客户端把 `HTTP/1.0 400 Bad Request` 当成没有冒号的头，于是报连接损坏并重试。

- `GET /mcp` 改为传入 `[("Allow", "POST")]`
- `_pairs` 若收到字典，改成按键值展开，避免再把状态行写两次
- `tests/test_mcp.py` 用原始套接字确认响应里只有一条状态行

正在跑的 `store serve` 要重启后，这个改动才生效。

## 2026-11-16 W1（第六刀）：每线程连接与只读快照

- `StoreBase` 的连接层改为每线程一条 SQLite 连接：文件库用 `threading.local` 懒建，线程退出随 thread-local 回收；主线程复用主连接；`:memory:` 回落主连接，并让读也走同一把锁，避免事务嵌套。
- 读方法不再拿全局写锁：`search`、`list_versions`、`describe`、`resolve_package`、`make_install_plan`、`artifact`、`list_reviews`、`get_review`、`list_my_submissions`、`get_submission`、`whoami`、`list_accounts`、`identity_status`、`has_principals`、`explain_manifest` 改走 `_read()`。`_read()` 开一个只读事务，让一次请求里的多条查询看到同一个快照。
- `refresh_hub_if_due` 的常见路径（没有刷新令牌、还没到点）不再拿锁；只有确实要刷新时才进写锁，并在锁内二次确认，避免并发重复刷新。
- 写路径仍由 `_lock` 串行；跨连接写由 WAL 与 `busy_timeout=5000` 兜底。
- 新增 `tests/test_concurrency.py` 4 条：写锁持有期间读能完成、每线程独立连接、6 个并发提交不丢行、内存库仍可用。实测 10 个带 KEY 的并发读从串行约 350ms 降到约 84ms（鉴权仍每次 scrypt）。

- 读写锁公平性：当前读完全不排队，写可能被持续读饿着；量级小，先不做。

## 2026-11-16 W1（第七刀）：KEY 认证缓存

- 每次带 KEY 的请求都做一次 scrypt，是并发上不去的主因。新增进程内认证缓存：`_hash(key)` 定位，缓存 `Principal`、账号纪元与过期时间，TTL 10 秒，最多 1024 条。
- 失效：账号、KEY 或角色一变，`_bump_auth_epoch()` 整体清空缓存。`issue_account_key`、`set_account_role`、`disable_account` 三处已接。单进程里这就是即时失效；直接改库的外部变更最多迟 10 秒。
- 实测：10 个带 KEY 的并发读从串行约 350ms → 未缓存并发约 84ms → 缓存后约 3ms。
- 新增 `tests/test_auth_cache.py` 5 条：命中不再 scrypt、过期后重新比对、停用/改角色/换 KEY 都让缓存失效。全套 224 个用例通过。

没做的：

- 缓存是进程内的，多实例部署时各自持有，最多 10 秒的不一致。
- 没有把 `sessions` 或枢纽令牌纳入缓存；它们本来就走 sha256 查表，不是瓶颈。

## 2026-11-16 W1（第八刀）：注册查重不再扫全表

- `_fresh_key` 改为只按 `key_prefix` 查一次、命中就重试，不再对全表逐行 scrypt。随机 32 字节 KEY 值重复的概率可以忽略，指纹碰撞重试三次足够。
- 删除 `_reject_reused_key`。它原本承担的是「同一把 KEY 不重复」，但真正的值比对在注册路径上既昂贵又没有额外安全收益。

- 实测 12 个连续注册约 65ms/个，保持常数；旧实现随已有账号数线性增长。
