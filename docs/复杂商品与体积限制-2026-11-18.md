# 复杂商品、体积限制与上传拆分

日期：2026-11-18。回答三个问题：当前有没有统一 16MiB 限制、商店 MCP 会不会自动分拆、复杂插件是否需要加固设计。

## 1. 当前限制

不存在“所有商品统一 16MiB”的限制。

| 对象 | 当前上限 | 实现 |
|---|---:|---|
| 通用制品 zip（skill / mcp / mcp+skill / runtime） | 32MiB | `_MAX_BYTES` |
| 插件包 zip | 16MiB | `PLUGIN_ARTIFACT`，统计包内全部文件 |
| 知识包 | 8MiB | `MAX_PACK_BYTES`；单篇 256KiB |
| 单个 zip 解压后 | 64MiB | `MAX_UNPACKED` |
| 安装器单个下载 | 64MiB | `installer._MAX_DOWNLOAD` |
| HTTP 上传正文 | 约 43.7MiB | `_MAX_BODY`，覆盖 32MiB base64 膨胀 |

插件文档里的“单文件 2MiB”目前只是建议，代码没有逐文件校验。

## 2. 依赖运行时怎么算

每个商品、每个依赖都是独立制品、独立提交、独立限额：

```text
插件 A（自身 ≤16MiB）
  └─ depends.store → runtime B（自身 ≤32MiB）
```

- A 的 16MiB 不包含 B；
- B 按自己的 32MiB 卡；
- 安装计划不做 A+B 的总量聚合；
- runtime 可以通过 `add_platform` 分平台追加，每个提交各自受 32MiB 限制；一个 runtime 的多个平台资产合计可以超过 32MiB。

## 3. 商店 MCP 会不会自动分拆

不会。

- `begin_submit` 只接收一个 `manifest` + 一个 `byte_size`；
- `save_upload` 只保存一个 zip；
- `finish_submit` 只校验一个 zip；
- `store submit` 把一个目录打成一个 zip；
- `add_platform` 是作者显式发起的第二次提交，不是服务端自动拆分。

因此，“一个复杂插件里同时有运行时、技能、知识”不能靠一次上传让商店拆开。作者必须把它们做成多个商品，再用依赖关系组合。

## 4. 当前组合能力

支持：

- 技能依赖技能：`depends.skills`
- 技能/插件依赖 MCP：`depends.mcp`
- 技能/插件依赖 runtime：`depends.store`
- 插件依赖外部命令：`depends.external`
- `kind=mcp+skill` 自带 MCP 和技能
- 共享依赖按 `(id, version)` 去重

不支持：

- 插件依赖插件：没有 `depends.plugins`
- 任意商品依赖知识包：没有 `depends.knowledge`
- 插件+技能+知识作为一个 `kind`
- 自动把一个大 zip 按目录拆成多个商品

## 5. 建议的加固设计

### 5.1 不先盲目抬高上限

单纯把 16MiB/32MiB 改成 128MiB 会带来：

- 服务端 `save_upload` 仍整段读内存；
- MCP 提交仍走 base64，内存和 JSON 体积翻倍；
- 解压炸弹、审核工作量、磁盘占用同步放大；
- 安装器下载/解压上限也要同步调整。

### 5.2 按“资产”而不是“整个商品”放宽 runtime

推荐：

- runtime 每个平台资产单独限额，例如 64MiB 或 128MiB；
- 一个 runtime 多平台合计不设商品级硬顶，按账号/磁盘配额控制；
- 每次 `add_platform` 只提交该平台资产；
- 服务端增加流式上传、分块/断点续传、磁盘配额。

### 5.3 复杂组合用“引用”，不要用“大包”

推荐模型：

```text
bundle/suite（清单，可选）
  ├─ plugin A
  ├─ runtime B
  ├─ skill C
  └─ knowledge D
```

bundle 本身不携带大文件，只声明成员和版本范围；安装计划展开成员，继续按 `(id, version)` 去重。这样：

- 每个成员独立审核、独立版本、独立回滚；
- 插件不必把 runtime/知识塞进自己的 zip；
- 不会出现一个 200MiB 的插件包无法审核。

### 5.4 需要补的字段/规则

- `depends.knowledge`：让插件/技能声明知识包依赖，安装计划生成 `download + unpack` 到知识根；
- `depends.plugins`：如果确实需要插件依赖插件；同时要有环检测和加载顺序约束；
- `kind=bundle`（或 `suite`）：只引用成员，不内嵌制品；
- 依赖版本跨分支统一：目前只做同版本去重，不做 SAT/版本合并；
- 组合审核：bundle 发布时检查成员均已发布、kind 匹配、版本范围可解析。

### 5.5 上传路径的硬要求

如果提高上限，必须先做：

1. 流式/分块上传，不把整个 zip 读进内存；
2. 服务端磁盘配额与账号配额；
3. 解压前按条目声明大小拒绝炸弹；
4. 每个文件/总包大小、文件数、路径深度上限；
5. 恶意文件/可执行文件/符号链接检查；
6. 安装器下载与解压上限同步；
7. 大包审核策略（插件清单、代码抽查、分平台审核）。

## 6. 结论

- **16MiB 只是插件包上限**，不是商品统一上限，也不包含依赖 runtime；
- **商店 MCP 不分拆**，一次提交就是一个 manifest + 一个 zip；
- 复杂插件应拆成多个独立商品，用依赖组合；需要一键安装时再加 bundle/suite；
- 运行时的合理方向是**按平台资产放宽 + 流式上传 + 配额**，不是直接把全局 32MiB 抬大；
- 当前最值得补的是 `depends.knowledge`、bundle 清单和流式上传，而不是先改一个数字。
