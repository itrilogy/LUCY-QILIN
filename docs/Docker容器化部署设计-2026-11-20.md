# Docker 容器化部署设计（2026-11-20）

适用对象：栖林商店 `main`（`store serve`：门户 + `/v1/*` + `/mcp`）。目标环境：**单机、单进程、SQLite + 本地制品目录**。这是一份可执行的设计，不是"能跑起来"的示例——每个决定都写了理由、代价和回退方式。

## 1. 目标与边界

### 1.1 目标

- 准备好数据目录后，一条 `docker compose up -d` 起来就能用，且**默认不把 8787 暴露到公网**。
- 数据（SQLite + 制品）在宿主绑定目录里，容器可随时重建、回滚、迁移宿主。
- 备份/恢复是脚本化、可演练的，不依赖"记得停服务"。
- 升级是可回滚的，且升级前强制有一份备份。
- 运行面最小：非 root、无 capabilities、只读根、无 shell 依赖。

### 1.2 明确不做

| 不做 | 原因 |
|---|---|
| 多副本 / 水平扩展 | 写锁、限流桶、KEY 缓存、启动全量重建索引都是进程内状态。两个副本指向同一库会互相踩（见评审 P1-9） |
| 把 SQLite 放 NFS/SMB/云盘 | SQLite 依赖 POSIX 记录锁与 mmap 语义，网络文件系统上会出现"随机损坏"，且不可复现 |
| 把 TLS 放进应用进程 | 应用没有 TLS 实现，也刻意不引入 `ssl` 包装（反代负责，`QILIN_PUBLIC_BASE` 负责告知真实地址） |
| 用 `--scale` 做"高可用" | 同第一条。真要做 HA，先换 PostgreSQL + S3 兼容对象存储，那是另一次改造 |
| 在镜像里跑 cron | 备份要能在进程挂掉时照常跑，调度归宿主（cron / systemd timer） |

## 2. 拓扑

三种形态，按环境选一种。

### 形态 A：宿主已有反代（推荐，最省资源）

```text
Internet ──443──▶ 宿主 Caddy/nginx ──127.0.0.1:8787──▶ qilin 容器
                     │                                    ├─ /srv/qilin/data:/var/lib/qilin
                     └─ 复用 deploy/nginx.conf.example     └─ 只读根 + tmpfs /tmp
```

- compose 默认就是这一形态：`ports: 127.0.0.1:8787:8787`，公网只有宿主反代的 443。
- 反代必须覆写 `Host`、`X-Forwarded-Proto`、`X-Real-IP`；`.env` 里 `QILIN_PUBLIC_BASE` 与真实地址一致。
- 应用访问日志已把 `?ticket=` 脱敏；**反向代理自己的 access log 仍会记完整 URL**（含一次性上传票据，1 小时有效）。要么不记 `/v1/uploads`，要么在网关侧做同样的脱敏。

### 形态 B：容器内 Caddy（一键全栈）

```text
Internet ──443──▶ qilin-caddy 容器 ──qilin:8787──▶ qilin 容器
                    │ 自动 ACME、HTTP→HTTPS
                    └─ volumes: caddy-data, caddy-config
```

```sh
docker compose --profile edge up -d
```

- Caddy 自动签发/续期证书，数据在 `caddy-data` 卷里，重建容器不重签。
- 只在这个 profile 下开 80/443。

### 形态 C：完全离线内网

- 用形态 A，反代换成本地自签证书或直接内网 HTTP；
- 若走 HTTP：`QILIN_PUBLIC_BASE=http://qilin.intra`，会话 Cookie 不带 `Secure`（应用按 `public_base` 判断），**不要**让 `X-Forwarded-Proto: https` 出现在明文链路上（否则浏览器收不到 Cookie，登录后立刻掉会话，评审 P2-15）。
- 镜像离线分发：`docker save qilin:<tag> | gzip > qilin.tgz` → `docker load`。

## 3. 镜像设计

### 3.1 两阶段

| 阶段 | 基础镜像 | 做什么 |
|---|---|---|
| `builder` | `python:3.13-slim-bookworm` | 建 venv，装唯一的第三方依赖 `cryptography`（hub extra），`pip install --no-deps .`，预编译 `.pyc` |
| `runtime` | 同上 | 只拷 venv + `store` 包 + 四个脚本；建 `qilin` 用户；跑一次冒烟（门户资源必须在包里） |

- 基础镜像已带 `ca-certificates` / `netbase` / `tzdata`（官方 python slim 的 Dockerfile 里就有），运行阶段不再 `apt`，少一层也少一批 CVE。
- `cryptography` 用 manylinux wheel，构建期不需要编译器；只有枢纽验签需要它，但为了"镜像即开即用"默认装上（约 +4MB）。
- 构建参数：`PYTHON_VERSION`、`QILIN_UID`、`QILIN_GID`、`GIT_SHA`、`BUILD_DATE`（后两个只进 OCI label）。

### 3.2 运行面

| 措施 | 取值 | 说明 |
|---|---|---|
| 用户 | `qilin`，uid/gid 10001 | 数据卷属主与它对齐 |
| 根文件系统 | `read_only: true` | 运行时唯一可写的是数据卷与 `/tmp` tmpfs |
| capabilities | `cap_drop: ALL` | 进程不需要任何特权 |
| 提权 | `security_opt: no-new-privileges` | 防止 setuid 提权 |
| `/tmp` | tmpfs 16MB | 真正的临时文件走 `TMPDIR=/var/lib/qilin/tmp`（磁盘），见 4.2 |
| pid 上限 | `pids_limit: 256` | 每请求一线程，这是内存兜底不是并发配额 |
| 文件描述符 | 4096 | 128 连接队列 + 线程数留余量 |
| 信号 | `init: true` + 应用自处理 SIGTERM | 无僵尸进程；`docker stop` 走优雅退出 |
| 日志 | json-file，10MB × 5 | 防日志打满磁盘；生产建议改 journald 或 Loki |
| 资源 | `cpus: 1.0`，`memory: 512M` | 见第 10 节估算 |

镜像里**没有** `curl`、`git`、`gcc`、`pip` 的构建依赖；探针用 Python 标准库。

### 3.3 版本与标签

- 发布：`ghcr.io/itrilogy/lucy-qilin:v0.2.0`、`v0.2`、`latest`（workflow 里由 `metadata-action` 生成）。
- 生产固定到 `vX.Y.Z` 或 `@sha256:...`，**不要用 `latest`**——回滚时你需要一个确定的旧镜像。
- 建议同时打 `latest` 只用于内网试用。

## 4. 配置模型

应用自己只解析命令行参数，只有这几项直接读环境变量：`QILIN_PUBLIC_BASE`、`QILIN_HUB_ORIGIN`、`QILIN_HUB_AUTHORIZE`、`QILIN_HUB_SECRET`、`QILIN_APP_ID`、`QILIN_LOG_LEVEL`、`QILIN_TRUST_PROXY`、`QILIN_ACCESS_LOG`。其余容器约定由 `entrypoint.sh` 翻译成参数。

### 4.1 映射表

| 环境变量 | 默认 | 变成 |
|---|---|---|
| `QILIN_HOST` | `0.0.0.0` | `--host` |
| `QILIN_PORT` | `8787` | `--port`（容器内监听端口；compose 里固定 8787，宿主端口用 `QILIN_HOST_PORT`） |
| `QILIN_DB` | `/var/lib/qilin/qilin.db` | `--db` |
| `QILIN_BLOBS` | `/var/lib/qilin/blobs` | `--blobs` |
| `QILIN_PUBLIC_BASE` | 空 | `--public-base`（**反代后必填**） |
| `QILIN_HUB_ORIGIN` | 空 | `--hub-origin` |
| `QILIN_APP_ID` | 空 | `--app-id` |
| `QILIN_HUB_AUTHORIZE` | 空 | `--hub-authorize` |
| `QILIN_LOG_LEVEL` | `WARNING` | `--log-level` |
| `QILIN_TRUST_PROXY=1` | compose 里为 1 | `--trust-proxy` |
| `QILIN_HUB_SECRET` / `QILIN_HUB_SECRET_FILE` | 空 | 后者读文件内容进前者（Docker secret / k8s secret） |
| `QILIN_ACCESS_LOG=1` | 0 | 应用自己的访问日志（含 query，注意 P2-9） |
| `QILIN_TMPDIR` | `/var/lib/qilin/tmp` | `TMPDIR`，上传校验的临时目录 |
| `QILIN_REGISTRATION` | `open` | 自助注册开关（`open`/`closed`）；空库一律要先 `init-admin` |
| `QILIN_FETCH_POLICY` | `public` | 上传校验抓外部地址的策略：只公网 / 只白名单 / 全放开 |
| `QILIN_FETCH_ALLOW_HOSTS` | 空 | 内网资源白名单，逗号分隔主机或域名后缀 |

`QILIN_PUBLIC_BASE` 为什么必须配：应用在没有它时会用 `Host` 头推断对外地址（`store/http_api.py:826`），而 `Host` 是客户端可伪造的。推断出来的地址会被写进 MCP 配置、`put_url` 和安装计划里。配了它就以它为准，不再看请求头。

### 4.2 临时目录

上传校验会把 zip 解到 `tempfile` 目录：单包解压上限 64MiB（`store/blobs.py:13`），加上压缩包本身最大 32MiB。如果 `/tmp` 是 16MB 的 tmpfs，一次稍大的提交就会 `No space left on device`。所以 `TMPDIR` 指向数据卷下的 `tmp/`，tmpfs 只留给 Python 自己的零碎文件。

代价：容器被 `kill -9` 时会留下临时目录。入口脚本在**只跑 `serve` 时**清理 2 小时前的残留（one-shot 的 backup 不清，避免删掉正在运行的实例的临时文件）。

### 4.3 密钥

三种来源，按安全性排序：

1. **挂载文件**（推荐）：`QILIN_HUB_SECRET_FILE=/run/secrets/qilin_hub_secret`，compose 里把宿主文件只读挂进去。入口脚本读进环境变量后不落盘、不打印。
2. **`.env` 文件**：`.env` 在 `.gitignore` 里，`chmod 600`。`docker inspect` 能看到，仅限可信宿主。
3. **Docker secret / k8s Secret**：与第 1 种等价，只是编排层管理。

`.env` 里写了 `QILIN_HUB_SECRET` 又写了 `QILIN_HUB_SECRET_FILE` 时，文件优先（入口脚本先 `load_secret` 再拼参数）。

## 5. 存储

### 5.1 目录布局

```text
/srv/qilin/data  （宿主目录，绑定挂载到容器的 /var/lib/qilin）
  qilin.db               主库
  qilin.db-wal/-shm      WAL（必须与 db 同目录、同一块盘）
  jwks-cache.json        枢纽公钥缓存（有 --hub-origin 时才有）
  blobs/
    submissions/<sid>.zip        待审/已审的提交包
    releases/<id>/<version>.zip  已发布制品（与 submissions 各一份）
    assets/<sid>/<platform>      runtime 平台资产
    uploads/<sid>.zip            三段上传的中间件
  tmp/                   上传校验临时目录（可清）
```

compose 里是 `${QILIN_DATA_DIR:-./data}:/var/lib/qilin`。选绑定挂载而不是命名卷，是因为这批数据的迁移成本最低：**停服 → `cp -a` → 起容器**，不需要 `docker cp`、不需要 root 进 `/var/lib/docker/volumes`，备份与排查都直接看得见。命名卷也能用（把 compose 里那行换成 `qilin-data:/var/lib/qilin` 并声明 volume），代价是数据不在文件系统里直观可见。

`/backups` 另放一个绑定挂载，见第 7 节。

### 5.2 为什么必须是本地块存储

SQLite 在 WAL 模式下依赖：POSIX `fcntl` 记录锁、`mmap` 一致性、同目录 rename 的原子性。网络文件系统（NFSv3/SMB）常出现锁语义不一致，表现为：**偶发 `database is locked`、WAL 损坏、库打不开**，而且现场往往无法复现。

- 宿主 ext4/xfs 绑定挂载 ✅（属主要 chown 到 10001）
- Docker 命名卷（默认 `local` driver，ext4/xfs）✅
- Docker Desktop 的绑定挂载（virtiofs/gRPC-FUSE）⚠️ 仅开发用，性能与属主映射都和 Linux 不同
- NFS/SMB/云文件存储 ❌

### 5.3 属主与只读根

容器以 uid/gid `10001:10001` 运行，数据目录必须先建好并改属主：

```sh
sudo install -d -o 10001 -g 10001 -m 0750 /srv/qilin/data /srv/qilin/backups
```

属主不对时，入口脚本在启动前就会给出可操作的错误，而不是 SQLite 的 `unable to open database file`：

```text
qilin-entrypoint: error: 目录不可写：/var/lib/qilin（容器以 uid 10001:10001 运行；绑定挂载请先 chown，或改用命名卷）
```

### 5.4 带入现有数据（不丢商品）

从 systemd/本机部署切到容器，数据搬运用 [`deploy/docker/import-existing-data.sh`](../deploy/docker/import-existing-data.sh)，在宿主上跑，不需要 Docker：

```sh
sudo systemctl stop qilin            # 或停掉旧进程；有 qilin.db-wal 未合并时脚本会拒绝
./deploy/docker/import-existing-data.sh --source ./var --target /srv/qilin/data
docker compose up -d
```

脚本做四件事，顺序不能省：

1. **拒绝热拷**：源库还有未合并的 `qilin.db-wal` 时直接退出（确认已停服可 `--allow-wal`）；目标已有数据时默认拒绝，要覆盖必须 `--force`。
2. **复制**：`qilin.db`（连 `-wal`/`-shm`）、`jwks-cache.json`、整个 `blobs/`。不复制 `tmp/`。
3. **改属主**：root 下 `chown -R 10001:10001`；非 root 时警告。
4. **对账**：用 SQLite 只读打开源库与目标库，逐表比 `accounts/submissions/releases/release_assets/submission_assets/package_owners` 行数，比对制品文件清单，再对目标库跑 `PRAGMA integrity_check`。任何一项不一致 → 退出码 1，并提示不要带不一致的数据启动。

本机实测（2026-11-20，真实 `var/`）：

```text
accounts 3→3   submissions 19→19   releases 14→14
制品文件 34 个，与源一致
目标库 integrity_check：ok
```

随后用当前代码对着迁移副本起服务：`/api/health` 200、货架 `total=14`（14 个已发布商品全部在架）、匿名下载 `luxi.paiyun-pro 2.0.0` 得到 1,048,066 字节且 sha256 与库内记录一致。迁移前后源目录的 DB 行数未变——迁移是纯复制，不改源。

反向（容器 → systemd）就是反着 `cp -a` 一次；两侧用的是同一份目录结构。

### 5.5 磁盘增长

每个已发布版本会在 `submissions/` 与 `releases/` 各存一份 zip（评审 P2 已提到），runtime 另有 `assets/`。按"平均 10MB × 每月 50 个版本"估算 ≈ 1GB/月（双份）。备份再做一份 ≈ 2GB/月。

- 建议 `blobs/` 所在盘 ≥ 50GB，并配磁盘 80% 告警。
- 清理策略（需产品确认）：已发布且超过 N 天的 `submissions/*.zip` 是否可删——现在删了会影响审核历史回看。

## 6. 生命周期

### 6.1 启动

```text
entrypoint
  ├─ load_secret（QILIN_HUB_SECRET_FILE）
  ├─ check_data（mkdir + 可写检查，失败退出 78）
  ├─ clean_tmp（只清 2h 前的旧临时目录）
  └─ exec store serve --host … --db … --blobs … [--public-base …] …
        └─ Store.__init__：建表 → 结构迁移 → 重建 catalog 索引 → 恢复 validating → 清理过期上传
              └─ serve_forever()
```

启动日志会打印实际使用的库与制品目录（`数据库 /path/qilin.db`）。容器里看 `docker compose logs qilin` 第一屏就能确认它连的是 `/var/lib/qilin/qilin.db` 而不是工作目录下的 `var/`——CLI 本身不读 `QILIN_DB`，这一行是排错时最快的一眼。

启动耗时主要在两处：`_rebuild_catalog_index()` 按包逐个重建（包多时线性增长）、迁移里的 `ALTER TABLE`。第一次部署很快；存量库升级要留出时间，healthcheck 的 `start_period: 25s` 就是给它留的。

### 6.2 停止

```text
docker stop
  → SIGTERM → 应用：停止接收新连接 → drain（等在途请求，最多 25s）→ 关库 → exit 0
  → 若 stop_grace_period（30s）内没退出 → SIGKILL
```

- 应用侧的行为是本轮新增的（`store/cli/__init__.py` + `_Server.drain()`）。改动前 SIGTERM 直接打死进程（退出 143），在途上传被截断。
- **第二次 SIGTERM / SIGINT 立即退出**，运维不想等的时候不用等。
- `stop_grace_period: 30s` 比 drain 的 25s 大，留 5s 给解释器收尾。若你有超大制品上传，可以调大到 60s（应用侧 drain 上限也要跟着改）。

### 6.3 健康检查

| 探针 | 语义 | 用法 |
|---|---|---|
| `/api/health` | 200 = 库可读且制品目录可写；503 = degraded | 容器 HEALTHCHECK、Caddy `depends_on`、外部监控 |
| `GET /` | 门户 HTML | 人工确认 |
| MCP `initialize` | 协议可用 | 部署验收 |

`/api/health` 现在把"存活"和"就绪"混在一起：它是只读探针（不会重启进程），但 DB 短暂不可读时会让 Caddy 认为上游不健康。生产上建议把容器 HEALTHCHECK 保持为就绪语义，**不要**接成"不健康就重启"的自动动作（compose 默认不会）。真要自动重启，需要先做评审 §4.4 的 `/livez` + `/readyz`。

### 6.4 重启策略

`restart: unless-stopped`：宿主重启、OOM、崩溃都会拉起来；`docker stop` 之后不会自己回来。OOM 排查看 `docker inspect -f '{{.State.OOMKilled}}' qilin`。

## 7. 备份与恢复

### 7.1 备份一致性从哪来

`store backup` 用 SQLite 在线备份 API（`store/backup.py:51-59`）复制数据库——WAL 模式下也能拿到一致快照，不需要停服。制品目录用 `copytree`。

**已知边界**：制品写入是非原子的（`submissions.py:167` 直接 `write_bytes`），所以"备份正好与上传撞上"时可能抓到半个 zip；`backup.json` 会把半个文件也记进校验和（自洽，但内容是截断的）。概率低，但属于 P2-8，建议改成 `.part` + `os.replace`。在此之前，**备份安排在低峰**。

### 7.2 备份

```sh
# 立刻备份（compose 一次性任务；backup 在 ops profile 里）
docker compose --profile ops run --rm backup
# 产物：/srv/qilin/backups/<UTC 时间戳>/{qilin.db, blobs/, backup.json}
```

调度用宿主 cron：

```cron
15 3 * * * cd /opt/qilin && docker compose --profile ops run --rm backup >> /var/log/qilin-backup.log 2>&1
```

或 systemd timer（更好，有失败重试与日志）：

```ini
# /etc/systemd/system/qilin-backup.service
[Unit]
Description=Qilin backup
[Service]
Type=oneshot
WorkingDirectory=/opt/qilin
ExecStart=/usr/bin/docker compose --profile ops run --rm backup
```

```ini
# /etc/systemd/system/qilin-backup.timer
[Unit]
Description=Daily qilin backup
[Timer]
OnCalendar=*-*-* 03:15:00
Persistent=true
[Install]
WantedBy=timers.target
```

保留：`QILIN_BACKUP_KEEP`（默认 14 份，按份数不按天数）。清理只删"备份根下一级目录"，不动文件与软链。

**RPO**：默认 24h。要更小就每小时跑一次（体积小的话成本很低）。
**异地**：`restic` / `rclone` 推 S3 / 另一台机器；备份目录本身就是普通目录，不需要应用配合。

```sh
restic -r s3:s3.example.com/qilin backup /srv/qilin/backups --tag qilin
```

**加密**：`backup.json` 里是明文路径与校验和，`qilin.db` 里有 KEY 明文（当前取舍）。备份介质必须加密或放在受控位置。

### 7.3 恢复

```sh
docker compose stop qilin
docker compose --profile ops run --rm --entrypoint /usr/local/bin/qilin-restore \
  -e QILIN_RESTORE_CONFIRM=yes backup 20261120T030000Z
docker compose start qilin
docker compose exec qilin /usr/local/bin/qilin-healthcheck
```

- 恢复前会逐个核对 `backup.json` 里的 sha256，任何一项不符整体拒绝。
- 恢复命令会先尝试拿数据库旁的 `<db>.lock`：**服务还在跑就直接拒绝**（flock 在容器与宿主间共用内核），挡住"忘了停服就恢复"。
- 会覆盖 DB 与 blobs（内部 `--force`）。
- 恢复后 KEY 回到备份时的状态：**备份之后重新生成的 KEY 会失效**，需要通知作者重新取 KEY。
- 季度演练一次，演练记录写进运维日志（RTO 实测）。

**RTO**：数据量 < 5GB 时，停服 + 恢复 + 启动 ≈ 2–5 分钟。

## 8. 升级与回滚

### 8.1 升级

```sh
cd /opt/qilin
docker compose --profile ops run --rm backup    # 1. 备份（失败就停）
sed -i 's|^QILIN_IMAGE=.*|QILIN_IMAGE=ghcr.io/itrilogy/lucy-qilin:v0.2.0|' .env
docker compose pull                            # 2. 拉新镜像
docker compose up -d                           # 3. 重建容器（数据库迁移在启动时跑）
docker compose ps                              # 4. qilin 变 healthy
docker compose logs -f --tail=100 qilin
```

迁移策略是"启动时幂等执行 + `PRAGMA user_version`"（`store/base.py:215`），没有独立的 `migrate` 命令。这意味着：

- 升级前必须备份（迁移一旦跑了半截，没有自动回滚）。
- 迁移是**前向**的：旧镜像读到新库可能不认识新列/新表，回滚要连数据一起回。
- 每次改 schema 都要同时抬 `_SCHEMA_VERSION` 并写迁移分支；这一条应进发布 checklist。

### 8.2 回滚

```sh
docker compose stop qilin
sed -i 's|^QILIN_IMAGE=.*|QILIN_IMAGE=ghcr.io/itrilogy/lucy-qilin:v0.1.0|' .env
docker compose up -d
```

如果新版本已改过库结构：先恢复升级前那份备份，再启动旧镜像（顺序不能反）。

### 8.3 镜像来源

CI（`.github/workflows/docker.yml`）在 `v*` tag 上构建 `linux/amd64` + `linux/arm64`，产出 SBOM 与 provenance，推 GHCR，并用 Trivy 扫 `CRITICAL/HIGH`（`ignore-unfixed`，避免被无法修的告警淹没）。生产只拉自己 CI 产出的镜像。

## 9. 安全基线

### 9.1 网络

| 项 | 做法 |
|---|---|
| 暴露面 | 只有反代 443（+80 做跳转/ACME）。8787 只绑 `127.0.0.1` |
| 反代 → 应用 | 同一 compose 网络的 `qilin:8787`，不经宿主端口 |
| `Host` / `XFP` | 反代强制覆写；应用 `QILIN_PUBLIC_BASE` 固定 |
| 连接数 | 反代侧限并发（Caddy 用 `limits` 插件，nginx 用 `limit_conn`），挡慢连接——应用是每请求一线程，没有并发上限 |
| 请求体 | 反代 64MB 上限；应用自身 44MB（32MiB 制品 base64 后的余量） |

### 9.2 应用侧需要配合的（代码未改，部署时必须知道）

1. **注册与管理员引导**（评审 P1-2，2026-11-20 已修）：空库不再把 HTTP 注册者变成管理员，管理员只能由 `store init-admin` 建；`QILIN_REGISTRATION=open|closed` 控制自助注册（默认 `open`）。**首次上线仍要按 §11 的顺序做**：先只起应用、本机跑 init-admin，再接 443。公网部署建议 `QILIN_REGISTRATION=closed`，由管理员在「用户管理」里开号。
2. **限流在进程内**：多实例不共享；本设计只有单实例，够用。反代再加一层是纵深防御。
3. **KEY 明文**：DB、备份、`/v1/me` 都有明文（评审 P1-6）。数据卷权限 0750、备份加密、不把 `qilin.db` 当普通文件传。
4. **SSRF**（评审 P1-3，2026-11-20 已修）：上传校验抓外部地址时默认只允许公网——回环、私网、链路本地（含 `169.254.169.254` 元数据地址）一律不访问，重定向每跳重新校验且禁止 https→http，单份清单最多 20 个地址、45 秒预算。内网资源用 `QILIN_FETCH_ALLOW_HOSTS` 开白名单，不要把策略改成 `any`。残余风险：DNS 在检查与连接之间重新解析，理论上存在重绑定窗口。

### 9.3 镜像与供应链

- 基础镜像固定 tag，生产再固定 digest。
- CI 出 SBOM + Trivy；镜像层面没有再装包，攻击面主要是 Python 与 libsqlite3。
- `read_only` + `cap_drop` + `no-new-privileges` 让"打进来之后能做什么"压到最低。
- 不要把 `.env` 打进镜像（`.dockerignore` 已排除 `.env*`、`var/`、`deploy/docker/secrets/`）。

### 9.4 密钥轮换

- `QILIN_HUB_SECRET` 轮换：改 `.env`/文件 → `docker compose up -d`（重建容器）→ 旧密钥立即失效。
- 账号 KEY 轮换走门户"重新生成"，无容器操作。

## 10. 容量与性能

### 10.1 内存

| 来源 | 估算 |
|---|---|
| Python 解释器 + 模块 | 35–50MB |
| 每请求线程栈 | ~8MB 虚拟，实际按页 |
| scrypt（登录/注册/KEY 校验） | 16MB/次，峰值并发 5–10 → 80–160MB |
| 制品下载 | 32MiB/次，整块进内存（`_read_artifact`） |
| zip 解包校验 | 落盘，不占内存 |

512MB 适合"十几个并发 + 偶发登录"。如果出现多位作者同时上传大包，调到 1GB 更稳。

### 10.2 CPU

单核够用。瓶颈在：scrypt（约 50–100ms/次，且在全局写锁内）、启动时重建索引、上传校验（解包 + URL 探测）。`cpus: 1.0` 是保守值；给 2 核可以减少上传并发时的排队。

### 10.3 连接的代价（代码层事实）

`ThreadingHTTPServer` 每个连接一个线程，`_db` 每线程一条 SQLite 连接，而 `protocol_version` 是 HTTP/1.0（每请求一条连接）。所以门户一次加载 5 个静态资源 = 5 个线程 + 5 次 `sqlite3.connect` + 5 次 `PRAGMA journal_mode=WAL`。在当前规模（内网、几十人）没问题；要提速先做评审 §4.5 的 keep-alive 与静态资源缓存，比换框架划算。

### 10.4 单实例上限（经验值）

| 指标 | 舒适区 |
|---|---|
| 请求速率 | < 50 req/s |
| 制品总量 | < 50GB |
| 包数量 | < 5,000（启动索引重建是 O(包数)） |
| 同时在线作者 | < 50 |

超过就该考虑"读路径拆出去"（静态化货架 + 对象存储直链），而不是加副本。

## 12. 故障处置

| 现象 | 先看什么 | 常见原因 / 处理 |
|---|---|---|
| 容器反复重启 | `docker compose logs --tail=50 qilin` | 数据目录不可写（第 5.3 节）；端口被占；迁移失败（回滚到备份）；第二个实例被 flock 拒绝（看日志里的锁提示） |
| `healthy` 一直是 `starting` | `docker inspect --format '{{json .State.Health}}' qilin` | 启动重建索引慢（包多）；`start_period` 调大；DB 锁住 |
| 反代 502 | `docker compose ps`；容器内 `qilin-healthcheck` | 应用在重启；Caddy 与服务不在同一网络 |
| 登录后立刻掉会话 | 是否走 HTTPS；`QILIN_PUBLIC_BASE` 是否 https | `X-Forwarded-Proto: https` 出现在明文链路（评审 P2-15） |
| 上传报「目录不可写」 | `docker compose exec qilin id`；`ls -ld /srv/qilin/*` | 绑定挂载属主不是 10001 |
| 备份报「备份根目录不可写」 | `ls -ld /srv/qilin/backups` | 同上；或 `QILIN_BACKUP_DIR` 写错 |
| 恢复被拒 | 备份目录里是否有 `backup.json`；校验和是否完整 | 备份被改动/拷贝不完整 |
| 磁盘涨得快 | `du -sh /var/lib/qilin/blobs/*` | `submissions` 与 `releases` 双份 + 备份；见 5.5 |
| `database is locked` | 是否起了第二个容器/进程 | 单实例约束；`docker compose ps -a` 查有没有残留 one-shot |
| 上传报「地址当时打不开」但地址本身正常 | `QILIN_FETCH_POLICY` 与白名单 | 默认只允许公网；内网地址要加进 `QILIN_FETCH_ALLOW_HOSTS` |
| 发布报「制品不在磁盘上 / 校验和不一致」 | 提交件是否被清理、磁盘是否换过 | 发布前会核对制品存在与 sha256（P2-5）；重新上传提交一次 |
| 注册返回「商店还没有管理员」 | 是否跑过 `store init-admin` | 空库不开放 HTTP 注册，这是刻意的；先在容器里跑 init-admin |
| 注册返回「本店暂不开放注册」 | `.env` 里的 `QILIN_REGISTRATION` | 设为 `open`，或由管理员在「用户管理」里开号 |
| 启动报「另一个 store serve 正在使用 …」 | `docker compose ps -a`；宿主机上有没有第二个实例 | 单进程单副本约束；停掉多余实例。锁文件是 `<db>.lock` |
| 数据看起来是旧的（新商品不见了） | 启动日志里的「数据库 …」是哪一条路径 | 多半是绕过了入口脚本直接 `store serve` 且没传 `--db`：CLI 不读 `QILIN_DB`，会落到 `var/`。用 `docker compose exec qilin` 起命令时也注意这一点 |
| 部署后 OOMKilled | `docker inspect -f '{{.State.OOMKilled}}' qilin` | 并发大包上传；调 `QILIN_MEMORY` |

## 13. 与现有部署方式的关系

仓库里已有 systemd / launchd 方案（`deploy/qilin.service`、`deploy/com.lucy.qilin.plist`）与宿主反代示例。容器化不是替换关系：

| 维度 | systemd（现状） | Docker（本设计） |
|---|---|---|
| 适用 | 已经有 Python 环境的宿主、要求"零额外依赖" | 多环境一致、快速重建、回滚 |
| 数据位置 | `/var/lib/qilin` | 宿主目录绑定挂载（`QILIN_DATA_DIR`） |
| 备份 | 宿主 cron 调 `store backup` | 同一脚本，包在一次性容器里 |
| 安全边界 | systemd 沙箱（`ProtectSystem=strict` 等） | 容器 + 只读根 + cap_drop |
| 迁移 | — | 两边都是"停服 → 拷 `qilin.db` + `blobs/`" |

两者可以共存同一份数据目录，但**不要同时启动**（单实例约束）。
