# 反馈：`kind=mcp` 的制品拿不到，stdio 型 MCP 装不上

- 反馈日期：2026-11-24
- 反馈来源：用商店 MCP 实际安装一个上架商品
- 涉及商品：`luxi.chengju-chart-mcp@3.6.3`（澄矩 · ChengJu（IQS）专业绘图 MCP，作者 kwangwah）
- 客户端/平台：DeepSeek Harness，darwin-arm64
- 性质：制品与安装计划的一致性问题（非该商品独有）

## 一、现象

按商店给的标准流程走：`search → list_versions → resolve → describe → install_plan → artifact`。

1. `artifact` 取制品失败：

   ```
   artifact(id=luxi.chengju-chart-mcp, version=3.6.3, platform=darwin-arm64)
   → VERSION_UNAVAILABLE: 这个产品没有可下载的制品
   artifact(id=luxi.chengju-chart-mcp, version=3.6.3)（省略 platform）
   → VERSION_UNAVAILABLE: 这个产品没有可下载的制品
   ```

2. 但同一版本能正常 `describe`、`resolve`、`list_versions`，也能出 `install_plan`。`install_plan` 返回：

   ```json
   {"op": "ensure_bin", "name": "python3", "detect": ["python3 --version"]},
   {"op": "mcp_add", "id": "luxi.chengju-chart-mcp", "transport": "stdio",
    "command": "python3", "args": ["-u", "sse_bridge.py"]},
   {"op": "verify", "id": "luxi.chengju-chart-mcp", "version": "3.6.3", "kind": "mcp",
    "transport": "stdio", "command": "python3", "args": ["-u", "sse_bridge.py"]}
   ```

3. 计划里**没有任何取文件/解压的步骤**，而 `args` 指向的 `sse_bridge.py` 只可能来自制品。商品说明也明写“随包提供零依赖 Python 桥接脚本 `sse_bridge.py`”。

结果：文档说随包带脚本，下载说没有制品，计划又要求执行该脚本。三处互相对不上，安装器无法按计划完成安装。

## 二、影响

- 只要 stdio 型 MCP 需要随包脚本或本机二进制（桥接、代理、包装器），这份商品就不可能装成功。
- 用户拿到的失败是 `VERSION_UNAVAILABLE`，看起来像“版本不存在/下架”，容易被误判成商品没了，而不是“这个种类不做制品分发”。
- 该商品声明的远端只有 Legacy HTTP+SSE（`http://10.37.87.25:8083/sse`；`POST /mcp` 返回 404），而客户端只支持 stdio 或 streamable-http，桥接不是可选项，因此这条路径无法绕过。
- 本次的实际后果：只能由客户端自己写一份等价桥接脚本落地，再手工写 MCP 配置。商店的 `install_plan` 事实上没被采用。

## 三、需要澄清的两个口径

同一仓库里三处说法不一致，建议先定口径再谈修法：

1. 上架规范（`get_spec name=mcp` / `qilin://spec/mcp`）：“远程地址且没有本机依赖时，platforms 才能是 `["any"]`”“纯远程可以只交 manifest.json，没有 zip”——暗示非纯远程的 mcp 应当有制品，但没写“必须有”，也没写相对路径脚本怎么随包分发。
2. 设计正文（`agent-store-design.md` 第 4 节）：“MCP 与 `runtime` 这类工具按平台管理制品：一个版本可以有多份资产，每份对应一个平台。缺的平台以后用 `add_platform` 补”。
3. `get_spec name=runtime` 与 MCP 工具描述里写的却是“技能、MCP、知识包不能追加平台”“add_platform 只给 runtime”。

即：MCP 到底算不算“按平台管理制品”的种类，现有文本有两种互斥答案。

## 四、建议（供评审，不指定实现）

按“先定口径，再补能力或补校验”的顺序：

- **口径 A：MCP 支持携带制品。** 则需同时补：`artifact` 对 `kind=mcp` 可下载（单 zip 或按平台资产）、安装计划里有对应的取文件/落地步骤、以及 `add_platform` 与 `platforms` 的关系说明。
- **口径 B：MCP 不携带制品，只写连接。** 则校验阶段就应拦住这类包：stdio 的 `command` 必须是系统已有命令（如 `npx`、`uvx`、绝对路径），`args` 不得引用相对脚本；说明里也不应出现“随包提供脚本”的承诺。

无论选哪条，建议补一条校验：**manifest 的 `args`/`command` 里引用的本地文件，要么能由本版本制品提供，要么在提交时就判为不可安装**，避免“计划可生成、安装必失败”的包进入已发布状态。

## 五、可验收的判定

- 口径 A：对一个声明 stdio + 随包脚本的测试 MCP，`artifact` 返回 200 与 sha256，`install_plan` 含取文件步骤，按计划装完后 `verify` 通过。
- 口径 B：同样输入的清单在 `validate` 阶段即返回 error（规则 id 由商店定），`begin_submit` 被拒。
- 两种口径下，`artifact` 的失败信息都建议区分“没有这个版本”与“这个种类不做制品分发”，不要共用 `VERSION_UNAVAILABLE` 的同一句文案。
