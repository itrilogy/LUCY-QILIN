# 代码审计与演进规划

日期：2026-11-12。范围是栖林商店本仓库：校验、制品、安装计划、HTTP、门户页面。不包含技能仓库里已有目录的改造。

本文记录这一轮已经改的地方、还留着的风险，以及知识树只预留、不切换安装目录的约定。事实以当前代码为准。

## 2. 还留着的风险

- 32MiB 的请求体和制品仍然整段读进内存。上限只避免无界读取，不是流式处理。更大的包需要另做分块，而不是把上限再抬高。`_MAX_BODY` 现在是固定常量，没有做成配置项；改大它等于放宽内存占用。
- 审核差异用的是预览文本。超过 64KiB 的文件，差异只覆盖截断后的部分，不能当作完整 diff。
- `key_prefix` 只是定位用的指纹，真正的判断仍靠 scrypt。指纹相同的行会逐个比对，碰撞概率低但不是零，所以没有把它当认证凭据。旧库里 `key_prefix` 为空的行在首次成功认证前仍走全表比对，多实例同时首次认证会重复扫描。
- 残留上传的清理挂在启动与 `begin_submit` 上，没有独立定时任务。进程长期不启动、也不收到提交时，过期文件不会被清掉。72 小时是常量 `_UPLOAD_TTL_HOURS`，要改需改代码。
- 日志没有轮转，默认输出到 stderr，级别默认 `WARNING`。要长期留存得靠外部的日志收集，程序自己不切文件。鉴权失败日志里有规则名与客户端地址，不含口令与 KEY，但客户端地址取自 `X-Forwarded-For`，可以伪造，只用于定位，不作为证据。
- 对外地址没有显式配置时依赖 `X-Forwarded-Proto` 与 `Host`。`Host` 只校验外形，不校验是不是本域名。反代部署应当显式配置 `--public-base`，不要依赖请求头。
- `state` 绑定只在配置了 `--hub-authorize` 时真正生效：那时由商店签发 state，回调必须对得上。没配时跳转由枢纽自行发起，state 由枢纽决定，商店无从预知，代码只能照旧接受并在日志里记 `STATE_UNBOUND`。这条差别是刻意的，不要把它当成「已经全修好」。
- `--hub-authorize` 是一个含 `{state}`、`{redirect_uri}`、`{app_id}` 占位的字符串模板。商店只做字面替换，不解析、不校验这个地址，也不验证改完之后的 URL 是不是 http/https。它的取值来自部署者，属可信输入，但不能从请求里来。
- `/v1/identity` 里的 `hub_start` 只回答「配没配授权页」，不回答「那个地址现在能不能用」。它不为真时门户不显示登录入口；为真时也不保证跳过去一定有页面，失败会落到枢纽侧的错误页。这个字段不该被当成健康检查用。
- `describe` 的白名单只卡顶层键。`skill`、`mcp`、`runtime`、`knowledge`、`depends`、`secrets`、`invoke` 这些块里多出来的子字段仍会原样出现在详情里。schema 还没有把这些块收成封闭对象，安装器也是整块读取，所以没有在这一层再裁。不要把「顶层已收口」理解成「清单里任何新字段都不会公开」。
- 鉴权仍在全局锁内。`key_prefix` 只解决了逐行 scrypt 的成本，`ThreadingHTTPServer` 的实际并发度仍为 1。多人同时带 KEY 请求时排队，这一条没有改动。
- `tree_dest` 已经写进知识包的 `unpack` 步骤，当前安装器不读它。若有人把未知字段当成安装目录，会装错地方。安装器遇到不认识的 `op` 会停；遇到认识的 `unpack` 时只使用 `dest`。调用方不要自行改读 `tree_dest`。
- 忽略名单是固定名字加 `.storeignore` 的 fnmatch。它不扫描文件内容，也不能代替密钥扫描。
- schema 此前与 `KINDS` 不一致，是因为根对象 `additionalProperties` 为 true，校验器并不靠这份 schema 拒收 `knowledge`。现在枚举已经对齐。以后加种类时，两处要一起改。

## 3. 知识树：预留，不改落点

目的是以后能按业务类别、业务领域、知识种类把知识包放进一棵目录，供企业知识沉淀和语料使用。这一轮不建这棵树，也不迁移已经按 `<id>/<version>` 安装的包。

逻辑路径由 `resolve_knowledge_tree_path` 计算：

- `knowledge.taxonomy` 的 `business_category`、`business_domain`、`knowledge_kind` 三段都有，且每段匹配 `^[A-Za-z0-9_\-\u4e00-\u9fff]+$` 时，路径为 `<类别>/<领域>/<种类>/<id>/<version>`。
- 否则为 `_unclassified/<id>/<version>`。
- 段里出现斜杠或 `..` 时，路径退回 `_unclassified`，校验规则是 `KNOWLEDGE_TAXONOMY`。函数不返回带 `..` 的路径。

`knowledge.knowledge_map` 可选。只有在检查包内文件、且节点 id 或 file 对不上笔记时，才报 `KNOWLEDGE_MAP`。单篇题头的 `keywords`、`security_level`、`domain`、`knowledge_kind` 同样是写了才查。

安装计划里：

- `dest` 仍是 `${KNOWLEDGE_ROOT}/<id>/<version>`。
- `tree_dest` 是 `${KNOWLEDGE_ROOT}/` 加上上面的逻辑路径。

包的形态不变：根上只有 `manifest.json` 和 `.md`，没有子目录。知识树是包与包之间的摆放，不是包内目录。

以后若要真正按树安装，建议单独做，并先写清这几件事：

1. 安装器在哪一版开始改读 `tree_dest`，旧客户端不认识时如何失败，而不是装到错误目录。
2. 已安装的 `<id>/<version>` 是否保留，分类路径是移动、复制，还是只作索引。
3. 同一包修订 taxonomy 后，旧路径如何下线。未分类与已分类不要同时当成两份正文。
4. 分类段的词表由谁维护。现在只限制字符，不限制取值。
5. 语料抽取读哪条路径。在切换之前，只读 `dest`。

## 4. 门户行为

- 选择技能目录时，去掉第一层文件夹名。`manifest.json` 用来填 id、版本、标题、摘要、说明、变更、平台、AI 工具和作者显示名，不放进制品。`SKILL.md` 进文本框。其余文件按相对路径提交。`.DS_Store`、`._*`、`__MACOSX`、`.git` 等不提交。
- 选择笔记目录时，只保留相对路径里没有再嵌一层的 `.md`。子目录里的笔记不进入知识包，因为当前规则不收子目录。
- 审核页保留原来的清单差异。没有已发布版本时，清单差异仍显示「无已发布版本。」文件差异为空时，说明没有上一份制品，或正文没有变化。预览用 `textContent` 写入，不把文件内容当成 HTML。

## 5. 这一轮不做

- 不把知识包的安装目录改成分类路径。
- 不改技能仓库中的登记目录，不打开先前命中 `SECRET_FILE` 的文件，不放宽校验去接收旧目录。
- 不在商店服务器上执行安装。
- 不把知识地图做成图数据库，也不在商店里判断文章好不好。

## 6. 下一步：登记表不再充当集市资产名单

2026-11-13 记录。代码未改。第 14.4 节和 `store/validator/registry.py` 仍是现在的实现。本节只写变更方向，供后续手工修订规格，再改校验器。

### 6.1 现在错在哪里

`DIRECTORY_IDS` 把一批既有技能目录名映射成商店 `id`，`REGISTERED_IDS` 是这些 `id` 的集合。这批目录只是举例，说明「曾经有一批技能」，不是栖林商店的资产，也不是允许上架的名单。

当前两种判定因此都不合适：

- 解压目录名落在左列时，强制清单 `id` 等于右列，否则 `ID_RENAME`。目录名被当成了商品身份。
- `id` 不在这 27 个值里时，记警告 `ID_UNREGISTERED`，审核不确认就不能发布。新技能被当成「登记表之外」，而不是普通的新商品。

新技能现在仍能提交。警告是审核门，不是上传门。问题在于门的依据是一张示例对照，不是商店里已经存在的商品。

### 6.2 变更后的判定

只按「是不是已经在向商店声明身份」来分支。

1. 没有 `manifest.json`，或清单里没有核心标识的目录，不进入这张对照。技能目录照原有方式运行。商店不替它分配 `id`，也不因为它的目录名去套 `luxi.*`。
2. 有 `manifest.json`，且核心标识与商店里已有记录重叠时，必须校验，并做版本判别。重叠的对象是商店里的提交和已发布版本，不是目录名对照表。

这里暂把核心标识定为清单里的 `id`。同一 `id` 已存在时：

- 同一 `version` 已发布：维持现有 `VERSION_IMMUTABLE`，不能覆盖。
- 同一 `id`、新的 `version`：走现有的新版本提交，用 semver 判别先后，不另造一条商品。
- 商店里还没有这个 `id`：按新商品提交。不因为「不在示例表里」产生 `ID_UNREGISTERED`，也不要求审核人额外确认。

`validate` 仍只看清单。跨文件核对（例如题头与 `summary`）仍在读到包内文件时做，这与本节无关。

### 6.3 建议的改动顺序

规格修订完成后再动代码。顺序：

1. 改规格第 14.4 节：删掉「表外新技能先补登记表再分配 id」这句；写明示例目录不是资产名单。`ID_UNREGISTERED` 不再表示「不在这 27 个 id 里」。
2. 校验器去掉按目录名强制改 `id` 的 `ID_RENAME`，以及按 `REGISTERED_IDS` 打出的 `ID_UNREGISTERED`。`id` 的格式检查（小写 `命名空间.名字`）保留。
3. 同一 `id` 的版本冲突继续只用现有发布记录：已发布同版本不可变，新版本按 semver。不把目录名加入比较。
4. 审核页去掉「登记表之外，须人工确认才能发布」这个门。确认框只服务于这条警告；警告取消后，发布不再要求 `confirm_unregistered`。
5. 已发布的 `luxi.pandoc-slide-compiler@1.0.0` 保持原 `id`，不因这张表改名或下架。

### 6.4 修订时需要写死的两点

下面两点这次只按上面的理解记下来，规格正文由后续修订确定，不在这次改代码：

- 「核心标识」是否只有 `id`，还是 `id` 加 `version` 才算重叠。
- 「没有清单则正常执行」是否只指技能运行时不理商店；商店对这种目录的唯一行为是拒绝把它当成一件商品，而不是给它补一张清单。

以上两点由第 7 节定下来。第 6 节只保留「示例表不是资产名单」这个事实。

## 7. 从零做集市：身份、版本、提交前校验

2026-11-13。仍不改代码。第 14.4 节和 `registry.py` 继续是当前实现。本节是后续修订规格时要落成的设计，不是已上线行为。

另一份对 `pandoc-slide-compiler` 提交过程的评价，只采纳其中能对上代码的部分。不采纳评分，也不采纳「未登记 id 就是防冒领」。

### 7.1 集市里只有一种商品

商品是已经交进商店的清单，不是磁盘上的技能目录。

| | 技能目录 | 集市商品 |
|---|---|---|
| 给谁用 | 智能体按目录运行 | 商店货架、安装计划、版本选择 |
| 何时存在 | 目录在，就可以运行 | 清单进入商店并发布之后 |
| 身份 | 没有。目录名只是文件夹 | `id`。发布后不改 |
| 版本 | 没有商店版本 | `version`。已发布的同一版本不覆盖 |

没有 `manifest.json`，或清单里没有合法的 `id` 与 `version`：商店不分配 id，不查目录名对照，也不把它算作一件商品。这种目录继续由智能体运行。商店若被拿来提交它，只返回「这不是一件商品」，不为它补清单。

有合法 `id` 与 `version` 的清单，才进入下面的重叠判断。

### 7.2 核心标识与重叠

核心标识是 `id`。`version` 是这个 `id` 下面的一次发布，不是另一件商品。

重叠只和商店里的提交、已发布版本比较，不和任何目录名表比较。

- 商店里还没有这个 `id`：新商品。不警告，不要求「先写入某张示例表」，审核也不为「表外」额外确认。
- 已有这个 `id`，`version` 也已发布：`VERSION_IMMUTABLE`，不能覆盖。这是版本判别。
- 已有这个 `id`，`version` 是新的：同一商品的新版本，用现有 semver 分先后。
- 这个 `id` 已经由别的发布者发布：拒绝。防的是抢同一个商品名，不是「这个名字没出现在 27 行示例里」。

`id` 仍须是小写的 `命名空间.名字`。命名空间归第一个发布该前缀的发布者。这一条当前代码没有，单独做，不把 `DIRECTORY_IDS` 留作替代品。

因此去掉两件事：按目录名强制改写 `id` 的 `ID_RENAME`；按 `REGISTERED_IDS` 打出的 `ID_UNREGISTERED` 以及审核页上的确认门。`id` 格式不合法仍拒绝，规则名以后可改，避免和「目录名必须改成表内 id」混用。

已经发布的 `luxi.pandoc-slide-compiler@1.0.0` 保持这个 `id`。它是商店里的一条记录，不按示例表改成 `luxi.pandoc-slides`。

### 7.3 那次提交里，什么该留，什么不该留

本机库里的事实：第一次 `3b40edb48ac5cdde`，11603 字节，`rejected`，规则是 `ID_UNREGISTERED`（警告）和 `FRONTMATTER_CONFLICT`（错误）。第二次 `7d0ee85cdc1ef399`，11608 字节，三个文件都在包内，发布时仍带 `ID_UNREGISTERED`，审核确认后为 `published`。`summary` 与题头 `description` 的比较是子串、区分大小写；第一次措辞对不上，退回符合当时的规则。

三段上传（`begin_submit`、PUT、`finish_submit`）保留。包不要放进 MCP 参数，否则又把文件正文塞进对话。

`validate` 只看清单，是为了这一条。它看不到 `SKILL.md`，所以给过 `ok: true` 不能当成包已经合格。缺口不在「再做一个把全文当参数的 validate」，而在工具说明没有写清它不检查什么。`finish_submit` 继续做跨文件核对。

退回后必须换新 `submission_id`，这是 MCP 工具列表造成的，不是服务做不到。`_revise` 已经允许 `pending` 和 `rejected`。发布者 MCP 只有 `begin_submit`，没有 `revise`，调用方只能再走一遍。已发布版本仍然不可改。未发布的退回单应能原单换包。

`ID_UNREGISTERED` 不是防冒领。那次警告只说明 `luxi.pandoc-slide-compiler` 不在示例表里。防冒领用第 7.2 节的「同一 `id` 归已发布它的那一位」。

### 7.4 落地顺序

规格正文由手工修订。代码按这个顺序，做完一项再进下一项：

1. 改第 14.4 节，使它与第 7.1、7.2 节一致。示例目录可以留在文档里当历史材料，不能再当校验输入。
2. 校验器删除目录名强制改 `id`，以及按示例 id 集合打出的 `ID_UNREGISTERED`。审核页去掉对应确认框。`VERSION_IMMUTABLE` 与 semver 不动。
3. 发布者 MCP 增加与 `_revise` 相同的修订。`validate` 与 `get_spec` 的说明写明：不读包内文件；题头、路径和同一 `id` 的版本冲突在 `finish_submit` 或修订时才查。
4. 命名空间归属单独做。没有它之前，不同发布者抢同一个新 `id` 仍靠先发布先得，并在审核时能看见发布者。不恢复示例表来补这个空档。
