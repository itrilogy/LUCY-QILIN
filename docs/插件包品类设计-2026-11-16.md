# 插件包品类设计（草案）

日期：2026-11-16。状态：设计评审，未实现。目标：讨论 `kind=plugin` 是否成立、边界在哪、依赖与审核怎么定。

## 0. 结论摘要

1. **插件应当成为一个品类，但它是「可执行代码」品类，不能和配置式 MCP 混在一起。** 配置式 bundle 仍然属于 `kind=mcp` 的 DSH 适配产物；`kind=plugin` 只收 Host/Client 代码。
2. **建议先做「预留 + 拒绝」**（`PLUGIN_NOT_SUPPORTED`），等 schema、审核清单、staging 安装链路齐了再开放提交。
3. **不建议一刀切禁止所有第三方代码，建议分 Tier：**
   - Tier A：零运行时依赖，可声明外部 CLI；作者可提交。
   - Tier B：允许白名单内的纯 JS 依赖（无 install script、无原生模块）；仅 admin/白名单作者。
   - Tier C：原生 `.node` 模块；v1 不开放。
4. **成员可以提交，审核归 admin** 是合理默认，但要加三条：分级提交、审核清单、禁止自审。当前只有一个 admin，开放前建议先有第二个 admin，或明确 break-glass 规则。
5. 插件与 Harness 同权、没有进程内沙箱，所以「审核」是唯一的安全边界；不能把 `capabilities` 声明当成权限系统。

## 1. DSH 插件机制（设计依据）

- DSH bundle 是一个 npm 包，`package.json` 用 `dsh.bundle.patch` 指向 YAML patch；patch 插入 Loader 行。
- **Host-only bundle 可以没有 dependencies、install scripts 或 build 工具**（安装版文档 `host-plugin.md` 明确写了这一点）。
- Client 插件的 `client.js` 由浏览器模块表加载；React 由宿主提供，不需要也不应该重复安装 React。非基线运行时导入要写进 `dsh.client.external`。
- Client UI 不要 `require('@deepseek-ai/dsh-client-ui-primitives')`；应通过 slot 注册自己的组件，使用宿主主题 token，自己写控件。
- 插件通过 `ctx` 拿服务：tools、sessions、agents、systemPrompt、credentials、config、slots 等；Host 侧可用 Node 运行时与内置模块。
- 安装由 `plugin_manager install_bundle` 完成；商店与参考安装器都不应代替用户安装。
- **插件在 Harness 进程内运行，权限与 Harness 相同**：能读凭据、发网络请求、改 UI、影响其他插件。没有沙箱。

## 2. 品类边界

| 维度 | 技能包 `skill` | MCP `mcp` | 插件包 `plugin` |
|---|---|---|---|
| 运行位置 | Agent 上下文 + 本机脚本 | 独立进程/远端 | DSH 进程内（Host/Client） |
| 交付物 | 目录 + `SKILL.md` | 一条连接声明 | npm 包 + patch + 代码 |
| 权限面 | 与 Agent 相同 | 独立进程 | **与 Harness 相同** |
| 安装 | 解压到技能目录 | 配置式 bundle / 客户端配置 | `plugin_manager install_bundle` |
| 审核重点 | 提示词、脚本、密钥 | 协议、工具面、鉴权 | 代码、依赖、生命周期、UI 注入 |
| 回滚 | 删目录/换版本 | 改配置 | 禁用/卸载/换版本 |

**配置式 bundle 不进入 `plugin` 品类。** 它没有可执行代码，安装的是连接声明；归 `mcp`。只有需要 Host/Client 代码才能成立的产品，才走 `plugin`。

## 3. 清单设计

```json
{
  "spec_version": 1,
  "kind": "plugin",
  "id": "lab.workflow-board",
  "version": "1.0.0",
  "title": "工作流看板",
  "summary": "把当前会话的子代理与后台任务做成一块可点开的看板。",
  "description": "……",
  "changes": "首个版本。",
  "author": { "display_name": "鹿溪实验室" },
  "platforms": ["any"],
  "clients": ["deepseek-harness"],
  "depends": { "store": [], "skills": [], "mcp": [], "external": [] },
  "secrets": [],
  "invoke": { "form": "install_plugin" },
  "plugin": {
    "form": "both",
    "entry": "index.js",
    "client": "client.js",
    "patch": "cordis.patch.yml",
    "files": ["index.js", "client.js", "cordis.patch.yml", "locale/*.json", "icon.svg", "docs/DETAIL.md"],
    "dsh": ">=1.5 <2",
    "locale": ["locale/zh.json", "locale/en.json"],
    "icon": "icon.svg",
    "capabilities": ["tools", "client-slots", "credentials:read"],
    "external": ["rg"]
  }
}
```

- `plugin.form`：`host` | `client` | `both`。`host` 必须有 `entry`，`client` 必须有 `client`，`both` 两者都要。
- `plugin.patch`：必须存在，且根上是 `- insert:` 列表；商店只做结构检查，不解析全部 Loader 语义。
- `plugin.dsh`：合法 semver range；审核时对照目标 DSH 版本，避免升级即崩。
- `plugin.capabilities`：审核对照用，不是运行时权限。枚举建议：
  `tools`、`client-slots`、`commands`、`services`、`network`、`credentials:read`、`credentials:write`、`filesystem:read`、`filesystem:write`、`process:spawn`、`session:read`、`session:write`。
- `plugin.external`：需要的外部可执行文件（`pandoc`、`ffmpeg`、`rg`、`git` 等）。安装器只检查是否存在，不自动安装。
- `invoke.form = install_plugin`；插件不是“加载即用”的技能，安装动作必须由用户在 Plugins 里确认。

## 4. 制品与包结构

- v1 用 **zip**，根上就是包内容：`package.json`、`index.js`、`client.js`、`cordis.patch.yml`、`locale/`、`icon.svg`、`docs/`。
- 包内 `package.json` 的 `name` / `version` 必须与清单一致；`scripts` 必须为空；`private`/`type` 保持 bundle 模板要求。
- 依赖：
  - Tier A：无 `dependencies` / `optionalDependencies`；只允许 `peerDependencies` 里的 `@deepseek-ai/*`。
  - Tier B：白名单内的纯 JS 依赖，必须锁版本、带 license、无 install script。
  - Tier C：原生 `.node`，v1 拒绝。
- 体积：建议 16 MiB 上限；单文件 2 MiB；不允许二进制可执行文件、符号链接、路径逃逸。
- `files` 白名单必须覆盖所有运行文件；商店与审核都按白名单检查，防止夹带。
- 不把第三方代码“复制进 client.js”来绕过依赖策略；这仍算第三方代码，审核要按 Tier B 处理。

## 5. 安装计划

新增两个 op，商店只产出数据，不执行安装：

| op | 行为 |
|---|---|
| `plugin_stage` | 下载 → sha256 → 解压到 `${PLUGIN_STAGING}/<id>/<version>`；核对 `package.json` 的 name/version；检查 `entry`/`client`/`patch` 存在；**不执行代码** |
| `plugin_confirm` | 打印 staging 路径与安装说明，返回 0；不调用 `plugin_manager` |

- `${PLUGIN_STAGING}` 由参考安装器解析为 `$DSH_HOME/plugins/staging`，或 `--plugin-staging` 指定。
- `verify` op 对 plugin 只做静态核对：文件存在、name/version、scripts 为空、依赖策略。
- 安装说明示例：
  `在 DSH 的 Plugins 里添加本地目录 <staging>/<id>/<version>，或让 agent 调 plugin_manager install_bundle。`
- 卸载/回滚由用户在 Plugins 里操作；商店只负责下架，不远程卸载已安装副本。

## 6. 校验规则

| 规则 | 检查 |
|---|---|
| `PLUGIN_MANIFEST` | `package.json` 存在；`name`/`version` 与清单一致；`scripts` 为空 |
| `PLUGIN_ENTRY` | `entry`/`client`/`patch` 存在且是包内相对路径；form 与文件匹配 |
| `PLUGIN_SCRIPT` | 无 `postinstall`/`prepare`/`build` 等生命周期脚本 |
| `PLUGIN_DEPENDENCY` | 按 Tier 检查 dependencies/peerDependencies；禁止原生模块 |
| `PLUGIN_CAPABILITY` | capabilities 在枚举内；`process:spawn` 与 `external` 一致 |
| `PLUGIN_DSH_VERSION` | `dsh` 是合法 range，且与商店支持的 DSH 版本相交 |
| `PLUGIN_ARTIFACT` | zip 根结构、白名单、体积、无符号链接/二进制 |
| `PLUGIN_REVIEW_REQUIRED` | 发布前必须有 admin 的代码审核记录 |
| `SELF_REVIEW` | 不能批准自己提交的插件（建议推广到所有品类） |
| `PLUGIN_NOT_SUPPORTED` | 品类未开放时的统一拒绝码 |

`KINDS`、`store.schema.json`、门户 `KIND_LABEL`、`get_spec` 的 `plugin` 规范、`qilin://spec/plugin` 都要同步；`spec_version` 保持 1。

## 7. 客户端表

现有 `CLIENTS` 没有 DSH，需要加：

| client id | capabilities |
|---|---|
| `deepseek-harness` | `skill_dir`、`mcp_stdio`、`mcp_http`、`plugin`、`local_bin` |

`platforms` 对纯 JS 插件为 `["any"]`；Tier C 原生模块必须列具体平台，v1 不开放。

## 8. 依赖策略与生产力边界

### 8.1 机制：没有 npm 依赖，不等于没有能力

Host 插件可用：

- Node 内置模块：`fs`、`path`、`child_process`、`crypto`、`zlib`、`stream`、`worker_threads`、`url` 等。
- 全局 `fetch` / `WebSocket` 做 HTTP、SSE、webhook。
- DSH 的 `ctx` 服务：tools、sessions、agents、systemPrompt、credentials、config、slots。
- 通过 `child_process` 调本机 CLI（pandoc、ffmpeg、libreoffice、rg、git、python 脚本）。
- 调远端 API，把重活交给服务端。

Client 插件可用：

- 宿主提供的 React 与 slot 机制，不需要自带 React/UI 框架。
- 浏览器 API：Canvas、File、Clipboard、IndexedDB、WebSocket、fetch、WebCodecs（视宿主/浏览器支持）。
- 主题 token、locale、宿主控件模式，不需要第三方 UI 库。

所以「零依赖」限制的不是“能不能接系统”，而是**复杂格式编解码、算法库、原生性能、现成 SDK**。

### 8.2 生产力估算

以下不是精确统计，是按能力来源做的工程估算；前提是允许“声明的外部 CLI + HTTP API”。

| 插件类型 | 零依赖可做度 | 说明 |
|---|---|---|
| 连接器/集成（GitHub、Jira、飞书、Notion、RSS、行情、天气） | 90%+ | fetch + 凭据；主要工作量在协议和 UI |
| Agent 工作流/编排（工具、子代理、会话、命令、提示词库） | 90%+ | DSH 服务本身就是能力 |
| 文本/文件/批处理（Markdown、JSON、CSV、日志、重命名、归档） | 85% | Node 内置足够；复杂 YAML/TOML 需自写小解析器 |
| Git/本地 CLI 包装（git、rg、pandoc、ffmpeg、libreoffice） | 80%+ | 需声明 `external` 并检查 |
| 简单 UI/面板/看板/设置页 | 90% | 宿主 React + slot + 主题 |
| 图像/PDF/Office 深度处理 | 30–50% | 无 sharp/pdf-lib/xlsx/pptxgenjs；靠 Canvas、CLI、远端 API 降级 |
| 音视频/OCR/原生系统集成（USB、串口、专有 DB 驱动） | 10–30% | 主要靠 CLI/API；原生模块做不了 |
| 综合 | **约 60–75%** 的常见生产力插件可零 npm 依赖交付；若连外部 CLI/API 也禁止，降到 40–50% | 估算值，不是承诺 |

结论：**“零依赖”不会让插件品类变成玩具，但会显著压低“重型格式处理”类插件。** 大多数高价值插件是连接、编排、界面和批处理，不靠 npm 库。

### 8.3 建议的分级，而不是一刀切

| Tier | 允许 | 提交/审核 | 理由 |
|---|---|---|---|
| A | 零运行时依赖；可声明外部 CLI | 作者可提交，admin 审核 | 供应链最小，审核可做 |
| B | 白名单纯 JS 依赖；锁版本、无 install script、无原生 | 仅 admin/白名单作者 | 需要看依赖与 license |
| C | 原生 `.node`、平台相关二进制 | v1 不开放 | ABI/平台/安全不可控 |

如果坚持“绝对零依赖”，插件品类仍然成立，但应公开说明：Office/PDF/图像/音视频类插件主要走 CLI/API，或不做。

## 9. 提交与审核权限

### 9.1 建议

**允许作者（`publisher`）提交，审核归 admin。** 这符合现有“作者提交、审核发布”的模型，也避免 admin 成为唯一的内容生产者。

但按 Tier 分级：

- Tier A：`publisher` 可提交，admin 审核。
- Tier B：仅 admin 或白名单作者可提交，admin 审核。
- Tier C：v1 不接受。

普通 `member` 角色仍不能提交；要提交先授予 `publisher`。

### 9.2 必须加的三条

1. **禁止自审**：`reviewed_by != publisher_id`。admin 自己提交的插件必须由另一个 admin 审核；只有一个 admin 时，admin 自提交插件应被 `SELF_REVIEW` 阻止，或走显式 break-glass（记录审计、说明原因）。
2. **审核清单是数据**：新增 `plugin_reviews` 表或在 `submissions` 加 `review_json`，保存审核人、时间、代码 sha256、逐项勾选、声明的 capabilities 与实际检查结果。`approve` 对 plugin 要求这份记录存在。
3. **审核与提交分离**：审核队列单独展示 plugin，不与技能/MCP 混在一起；审核页显示代码文件树、依赖、外部命令、capabilities、风险项。

### 9.3 审核清单（建议）

- 源码可读：无混淆/压缩到不可读、无动态 `eval`/`new Function`。
- 无未声明的 `child_process`、网络请求、凭据读取、文件写入。
- 依赖符合 Tier；锁文件、license、无 install script。
- 生命周期：`ctx.effect`/`ctx.on` 清理完整；不写 DOM/`document.body`；不覆盖应用根。
- UI：slot 选择、主题 token、locale、键盘/焦点行为。
- 兼容：`dsh` range、`dsh.client.external`、平台声明。
- 安全：不把密钥写进包；不读取与本插件无关的凭据；不上传用户数据到未声明地址。
- 可回滚：禁用/卸载后不留后台定时器、监听器、子进程。

### 9.4 工作量与风险

代码审核是插件品类真正的瓶颈。建议先用 Tier A + 小包试点，限制 16 MiB/单文件 2 MiB；审核不过就退回，不做“先发布后补审”。插件一旦安装就在 Harness 进程内运行，**下架不能远程卸载已安装副本**，所以审核必须前移。

## 10. 分期

| 阶段 | 内容 | 接受提交 |
|---|---|---|
| P0 | 本设计评审 | 否 |
| P1 | `KINDS`/schema/`deepseek-harness` 客户端 + `PLUGIN_NOT_SUPPORTED` | 否，明确拒绝 |
| P2 | `plugin_stage`/`plugin_confirm` + 审核清单 + Tier A admin 试点 | 仅 admin |
| P3 | Tier A 开放给 publisher；Tier B 白名单 | 是 |
| P4 | 签名/静态扫描/第二 admin 强约束 | 是 |

## 11. 需要决定的问题

1. 现在就开放 `kind=plugin`，还是先 P1「预留 + 拒绝」？建议先预留。
2. 制品用 zip，还是 `npm pack` 的 tgz？建议 v1 zip。
3. 依赖策略：绝对零依赖，还是 Tier A/B/C？建议 Tier 分级。
4. 是否允许外部 CLI（pandoc/ffmpeg/rg）？建议允许但必须声明与检查。
5. 原生模块 v1 是否完全禁止？建议禁止。
6. 作者可提交 Tier A，还是 plugin 全部 admin-only？建议 Tier A 开放、B/C 收紧。
7. 只有一个 admin 时，admin 自提交插件怎么处理？建议阻止自审，先补第二 admin。

## 12. 非目标

- 不做进程内沙箱；DSH 没有这个机制。
- 不自动安装插件；商店只托管、分级、给 staging。
- 不把配置式 MCP 重新包装成 plugin。
- 不在 v1 支持原生模块、自动更新、远程卸载。
